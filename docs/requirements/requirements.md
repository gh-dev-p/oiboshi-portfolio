# 要件定義書

**追星（oiboshi）**

- 対象プロジェクト：追星（oiboshi）
- 本書の位置付け：アプリの目的、対象、スコープ（コア機能・MVP・見送る機能）、非機能要件を定める
- 技術スタック：Flutter、Supabase、Firebase（FCM）、Cloudflare（ウェブサイト・メール）、RevenueCat
- 対象OS：iOS・Android

---

## 1. 目的・背景

- 推しの発信者の更新（配信・投稿・予定）は、YouTube・Instagram・X・ツイキャス・Twitch など、複数の SNS に散らばっている。ファンは、複数のアプリを行き来して追っている。
- 追星は、散らばった更新を、1つのアプリで追えるようにする（[コアバリュー](../concept/core-value.md)）。
- 事業は、発信者に課金してもらう形にする。発信者が、SNS を連携し、予定を登録する。ファンには、登録や入力を求めない。
- 発信者の SNS の更新は、サーバーが取って、保存する。ファンのアプリは、保存されたデータだけを読む。
- 一般公開（App Store・Google Play）を目指す。
- メインの対象は、ストリーマー（VTuber、歌い手・アイドルなど、配信とリアルイベントの両方をやる人を含む）。リアルイベントは、ストリーマーからつなげたい先にする（決定事項 1）。

## 2. 用語定義

| 用語 | 定義 |
| --- | --- |
| ファン | アプリを使って、発信者の更新を追う人。匿名でサインインする。ログイン方法（Apple・Google・X・Twitch）を結び付けることもできる |
| 発信者 | 配信・投稿・予定を、追星に出す人。SNS のアカウントを連携して本人であることを確かめる。基本プランは無料で、X の連携だけ有料（X連携プラン） |
| 推し | ファンがフォロー中の発信者 |
| 配信 | ライブ配信 |
| 投稿 | 長尺動画・ショート動画・画像・テキストの投稿 |
| 予約 | 配信の、開始予定の時刻 |
| イベント | 発信者が手動で登録する予定。プラットフォームを持たない（リアルのイベントなど）。1つのイベントは1つの公演。発信者が手で作る予定は、イベントだけ（2026-11-09） |
| 実績 | 実際に行われた配信と投稿 |
| 埋め込みビューア | ホームの推しレーンの下に置いて、配信を流すもの |
| 固定ビューア | 配信か推しの動画を、画面のいちばん上に据え付けて流し続けるもの。下部ナビのスイッチで出し消しする |

## 4. スコープ定義

MVP は、配信・投稿・カレンダーの3軸で作る。段階は、第1段階から第3段階まで。段階分けは、費用よりやりたいことを優先して決める。

### 4.1 コア機能

コアバリュー（推しの更新を、1つのアプリで追える）を実現する機能。これがないと、アプリの利用価値がなくなる。

- 推しのフォロー
- 配信中の判定と、ホーム・推しリストでの表示
- 投稿の取得と、タイムラインでの表示
- 予定のカレンダーとタイムスケジュールでの表示

### 4.2 Must

<kbd>第1段階</kbd>

- フォロー・解除と、推しの検索（名前・ID・SNS のアカウント）。推しがいない人には、おすすめを出す
- 配信：ツイキャス・Twitch・YouTube の配信中の判定。本人の配信の映像の再生（ホームの埋め込みビューアと固定ビューア）。固定ビューア（配信か推しの動画を流し続ける）
- 投稿：YouTube（動画・ショート）と Instagram（リール・投稿・カルーセル）の取得と表示。全画面の投稿ビューア
- 新着の表示（推しのアイコンの「NEW」の印、発信者ページの区切り）
- フォロワー数（SNS ごとの数と、合計）
- カレンダー：配信の予約の取得（ツイキャス・Twitch・YouTube）、イベント、実績の反映（見張る前の配信を含む）。タイムスケジュール、月のカレンダー、絞り込み。イベント一覧
- 配信開始のプッシュ通知（全体のスイッチと、推しごとのオン・オフ）
- 初回起動（ウェルカム、推しを選ぶ、通知の説明）。ファンの登録や入力は求めない
- アカウント：匿名サインイン、ログイン方法の結び付け（Apple・Google・X・Twitch。機種変更や入れ直しでの引き継ぎ）、大事な操作の前の再認証、退会（Apple のひも付けの取り消しを含む）
- 設定：画面モード（ライト・ダーク・端末に従う）、言語（日本語・英語）、お問い合わせ、退会
- ファンのカバー画像（推しのページのカバーを、自分の写真に変える）
- 発信者を表示しない。発信者とイベントの公演の通報（App Store Review Guidelines 1.2）と、運営による停止
- 発信者向け：登録、アカウント連携（本人であることの確認。YouTube・ツイキャス・Twitch・X・Instagram）、表示する内容の選択、プロフィールの編集（SNS からの取り込み、タイプ）、イベントの管理と登録（広告のリンクの印、チケットサイトの検索、URL からの読み取りを含む）、投稿の管理（自分の投稿を追星で隠す・また出す）、予定のデフォルトの長さ、プラン（基本プランは無料。X の連携は有料のオプション）、オーナーが退会した発信者の取り戻し

<kbd>第2段階</kbd>

- 投稿の X 対応（本人の投稿だけ。リポスト・リプライは取らない）。発信者向けの X連携プラン（月 290 円）

<kbd>v1.1.0</kbd>

- 届いた手応え：予定の事前通知（予定の種類ごとのタイミング。推しごとに切れる）。発信者に見せる数（通知を届けた人数・通知から来た人数・予定が見られた数・フォロワーの増え方。ファンは匿名の合計だけで、少ない数は丸める）
- リンクの投稿：発信者の共有のリンク（OGP のカード、App Store か発信者ページへ。Universal Link）、入れたあとの引き継ぎ（クリップボード）、QR
- 告知の画像：1週間の予定から、追星の QR とリンクを入れた告知の画像を作り、共有する
- 追いたい：ファンが未登録の人を SNS の URL か ID で申告する。登録したら知らせて自動でフォローにする。運営が多い順に声をかける
- スクリーンショットと ASO の仕上げ

詳細は、[機能仕様書（届ける・広める）](../design/specs/functional-spec-reach.md)を参照する。

### 4.3 Should / Won't-now

- TikTok の配信・ショート動画（第3段階）。公式 API で他者のコンテンツを取れないので、対応の可否は、第3段階で判断する。
- ニコニコの配信（ニコニコ生放送）・動画（ニコニコ動画）。取得の方法を調べてから、段階を決める。
- Instagram の投稿の取得を、発信者が連携したトークンで取る方式に変えること。Meta のアプリの審査とビジネス認証が要るので、最初の公開（v1.0.0）のあとに回す。v1.0.0 の Instagram は、本人を確かめたうえで、運営のトークン1つで Business Discovery を呼び、公開されている投稿だけを取る（機能仕様書 4.4.1）。
- 配信・投稿・予定の中身での検索（例：「マイクラ」で、マイクラの配信や、マイクラを配信する発信者を見つける）。MVP の検索は、発信者（名前・ID・SNS のアカウント）だけにする。
- 発信者の記事（ブログ・note・アメブロなど）の取得と、タイムラインへの表示。対象のサービス、取り方、利用規約と著作権の扱いは、今後の検討事項とする。
- 発信者の投稿から、AI がイベントの候補を見つけること（決定事項 1）。
- v1.2.0 以降：星あつめのキャラクターの演出とファンのダッシュボード（終わった配信への「良かった」「見れなくて悲しい」）、イベントの入力の整理（URL を貼るのを主にする）、使い方の分かりやすさ、公式のリンクのページ（Linktree の代わり。合算のフォロワー）、Instagram の手動の確認（決定事項 1）。

### 4.4 見送る機能（やらないこと）

- 発信者本人の配信以外を、アプリ内で流さない。
- アプリ内で YouTube 動画を見られることを、必須にしない。
- チャット・コメント・リアクションなど、ファン同士・ファンと発信者の交流の機能。
- ツイキャスの録画（アーカイブ）、Twitch の VOD・クリップの取得。YouTube は、RSS に載る配信のアーカイブを、動画として出す。
- X のリポスト・リプライ、Instagram のストーリーズ・インスタライブ、YouTube のコミュニティ投稿の取得。
- ファンのプロフィール（名前・アバター）。
- チケットの販売の状況と、受付（先行・抽選・一般発売）の日付を持つこと。

## 5. 非機能要件

### 5.1 鮮度

| 項目 | 要件 |
| --- | --- |
| 配信 | 配信が始まってから、画面に出るまで、最大で約2分 |
| 投稿（YouTube・X） | 投稿されてから、画面に出るまで、最大で約2分（YouTube は、RSS 自体の遅れが加わる） |
| 投稿（Instagram） | 投稿されてから、画面に出るまで、最大で約16分 |

配信と Instagram の値は、取得の間隔が既定のときのもの。間隔は、運営が変えられる（機能仕様書 4.8.1.2）。

### 5.2 費用・規模

- 費用が、ファンの人数ではなく、発信者の人数に比例するようにする。SNS の呼び出しは、サーバーが行う。
- X の取得は、取れた件数に課金される。X連携プランは、投稿の多い発信者では原価が売上を超えるが、最初は赤字を受け入れる。
- YouTube のクォータ、Instagram の呼び出しの上限など、発信者の人数に上限がある制約は、今後の検討事項とする。
- 費用と、発信者数の上限は、発信者数の想定を置いて試算する（必要技術とリスク 2.18）。人数が増えたら、試算し直す。

### 5.3 セキュリティ・プライバシー

- SNS のキー・トークンは、サーバー（Supabase のシークレット）だけに置く。アプリには持たせない。
- ユーザーのデータは、行ごとのアクセス制御（RLS）で、本人だけに限る。
- ファンは、匿名でサインインする。ユーザー ID は、ファンには見せない。お問い合わせの本文にだけ入れる。ユーザー ID を受け取ることは、プライバシーポリシーに書く。
- 発信者のなりすましを防ぐ。発信者の登録と、SNS の所有の確認は、省かない。確認済みの SNS のアカウントがない発信者は、発信者を探す一覧・検索・おすすめに出さない。出る発信者は全員が確認済みなので、確認済みの印は出さない（[機能仕様書](../design/specs/functional-spec.md) 4.2.2・4.6.1）。
- 秘密情報（トークン・シークレット・個人の連絡先）は、コミットしない。

### 5.4 権利・審査

- 配信の映像は、発信者本人の配信だけを流す。
- App Store・Google Play の審査要件を満たす（審査チェックリスト）。アプリ内でユーザーのデータを削除できるようにする（退会）。
- 広告のリンクは、広告と分かるように、「PR」と出す。
- 他社のサービスの名前・ロゴは、各社のブランドガイドラインに従って使う。

### 5.5 運用

- 動作確認は、リリースまで、本番の Supabase だけで行う。dev の環境は、リリースのあとで作る。
- 公開用のウェブサイト（プライバシーポリシー、利用規約、発信者向けの利用規約、特定商取引法に基づく表記、データの削除の手順）を、独自ドメインの HTTPS で公開する。URL は `/privacy`・`/terms`・`/creator-terms`・`/tokushoho`・`/data-deletion` に固定する。
