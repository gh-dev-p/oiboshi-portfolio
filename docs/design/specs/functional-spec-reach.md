## 1. 本書の目的・範囲

- v1.1.0 で足す、届ける・広める機能の振る舞いを定める。範囲と方針は、決定事項 1章「v1.1.0 の範囲」が正。
- 用語・ユーザーと発信者の区分け・既存の機能（配信開始の通知・フォロー・発信者の登録など）は、[機能仕様書](functional-spec.md)が正。本書では、`機能仕様書 4.3.3` のように章番号で参照する。
- 画面の構成は画面定義書、データの項目はデータ設計書で定める。どちらも、実装の Issue で本書に合わせて足す。
- 決まっていない値は、「案」と書き、決める Issue を添える。決まったら、案の印と Issue を外す。
- 状態は、「実装済み／未実装」だけで表す。

## 4. 各機能の詳細仕様

### 4.1 予定の事前通知

#### 4.1.1 予定の事前通知

| 項目 | 内容 |
| --- | --- |
| 機能概要 | フォロー中の推しの予定（予約とイベントの公演）が始まる前に、プッシュ通知で知らせる。知らせるタイミングは、予定の種類で分ける |
| 事前条件 | 通知の許可、全体のスイッチがオン、その推しの通知がオン |
| 関連画面 | 通知設定、発信者ページ |
| 入力項目・バリデーション | 推しごとの通知のオン・オフ（配信開始の通知と同じスイッチ） |

<kbd>補足・実装メモ</kbd>

- フォロー中の推しの予定は、すべてファンに届く。発信者が予定ごとに知らせるかを選ぶことはしない。
- ファンは、推しごとに通知を切れる。スイッチは、配信開始の通知（機能仕様書 4.3.3）の推しごとのスイッチ（`follows.notify`）と1つにまとめる。推しごとのスイッチを切ると、配信開始の通知と予定の事前通知の両方が止まる。
- 全体のスイッチ（`user_settings.notifications_enabled`）がオフなら、予定の通知も送らない。
- 端末の登録・送り先の消し方・文言の言語・アプリを開いているときの出し方は、配信開始の通知（機能仕様書 4.3.3）と同じにする。
- Android では、チャンネル「予定の通知」で出す（Android 公開のマイルストーンで合わせる）。

<kbd>知らせるタイミング</kbd>

| 予定の種類 | タイミング |
| --- | --- |
| 配信の予約（ツイキャス・Twitch・YouTube） | 開始の15分前 |
| イベントの公演 | 開始の日の前日の20時（日本時間）だけ（当日の朝などには送らない） |

- 送るかを決めるのは定時実行（機能仕様書 4.8.1。Edge Function `notify-schedules`）で、間隔は1分ごと。送るタイミングを過ぎてから見つけた予定（タイミングより後に登録・取得された予定）は、開始の前なら、見つけた回に送る。開始を過ぎていれば送らない。
- 1つの予定につき、1回だけ送る。送ったかの印は、予定に付ける。送ったあとに開始の時刻が変わっても、送り直さない。
- 発信者が配信中（配信中の判定、機能仕様書 4.3.1）のあいだは、その発信者の予約の事前通知を送らずに待つ（配信開始の通知に任せる）。予約の開始までに配信が終われば、その回に送る。開始まで配信が続けば、送らない。イベントの公演は、配信中でも送る。

<kbd>送る決まり</kbd>

- 送る相手：その発信者をフォローしていて、その推しの通知（`follows.notify`）と、全体のスイッチの両方がオンのユーザーの、登録したすべての端末（配信開始の通知と同じ）。
- 送らないとき：オーナーが退会した発信者（機能仕様書 4.6.6.2）と、停止中の発信者（機能仕様書 4.6.7）の予定。消された予定。発信者が表示するコンテンツ（機能仕様書 4.6.3）で出していない予約。連携を解除した SNS の予約。
- 通知の鍵（サービスアカウント）がサーバーにない・形が違うときは、送らず、送ったことにもしない（鍵を直したあと、開始の前の予定なら送る）。
- 中身：タイトルは「{発信者の名前}の予定」、本文は、予約なら「{開始の時刻}から{サービス名}で配信予定：{タイトル}」、イベントの公演なら「明日 {開始の時刻}から：{イベント名}」（案）。時刻は日本時間。前日の20時より後に見つけた公演を当日に送るときは「明日」を「今日」にし、終日の公演は時刻を書かない。英語は、タイトルが「Upcoming from {発信者の名前}」、本文が「Live on {サービス名} at {時刻} JST: {タイトル}」・「Tomorrow at {時刻} JST: {イベント名}」（案）。同じ予定の通知は置き換え、開始を過ぎて届かなかった通知は捨てる。
- 通知を届けた数を、発信者に見せる数（4.2.1）に記録する。

<kbd>受け取ったとき</kbd>

- 通知を押したとき　→　アプリを開き、その予定の詳細（シート）を開く。初回起動が済んでいなければ、済んでから開く（画面定義書 5.1.6）。
- アプリを開いているときに届いたとき　→　配信開始の通知と同じく、スナックバー（通知のタイトルと「開く」）を出す。
- 押して開いたことを、発信者に見せる数（4.2.1）に記録する。

> <kbd>異常系</kbd>
>
> - 送れない　→　記録だけを残し、送り直さない
> - 予定がもう消えている（押したとき）　→　その発信者のページを開く

### 4.2 発信者に見せる数

#### 4.2.1 数の記録

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者ごとに、通知を届けた人数・通知から来た人数・予定が見られた数・フォロワーの増え方を、日ごとに数える |
| 事前条件 | なし |
| 関連画面 | なし（記録は、アプリとサーバーが裏で行う） |
| 入力項目・バリデーション | なし |

<kbd>数えるもの</kbd>

| 数 | 数え方 |
| --- | --- |
| 通知を届けた人数 | 配信開始の通知（機能仕様書 4.3.3）と予定の事前通知（4.1.1）を、FCM が受け付けた送り先のユーザーの数。同じ日に同じ人へ何回送っても、1人と数える |
| 通知から来た人数 | その発信者の通知を押して、アプリを開いたユーザーの数。同じ日に同じ人が何回開いても、1人と数える |
| 予定が見られた数 | その発信者の予定の詳細を開いたユーザーの数。同じ日に同じ人が同じ予定を何回開いても、1回と数える |
| フォロワーの増え方 | 追星でその発信者をフォローしたユーザーの数と、解除したユーザーの数。日ごとの差と、日の終わりのフォロワー数 |

- 日の区切りは、日本時間の0時にする。
- 通知を届けた・通知から来た・予定が見られたは、配信ごと・予定ごとにも数える（2026-11-15 本人）。記録には、対象（配信開始の通知はその配信、予定の事前通知と予定の詳細はその予定）を持つ。同じ日に同じ人が同じ対象で何回あっても、1回と数える。
- ファンの記録は、同じ人を数え分けるためだけに使う。発信者にも、ほかのファンにも、誰が何をしたかは出さない。
- 日ごとに数えたあとは、ユーザーを含む記録をすぐに消す。日本時間の0時5分に前の日を数え、数え終えた記録をその場で消す。ユーザーが分かる記録は、合計にしたら遅くとも次の日までに消す（2026-11-15 本人。プライバシーポリシーもこの前提）。残すのは、発信者ごと・日ごとの合計と、配信・予定ごと・日ごとの合計だけ。
- フォローした・解除したは、フォローの表から数える。どこから来たフォローか（共有のリンクからか）は分けない（ファンが共有のリンクを共有しても、数え方は変わらない）。ログインでフォローを足し合わせたとき（機能仕様書 4.1.4）は、同じ人のフォローを移すだけなので数えない。
- フォロワー数は、日の終わり（数えた時点）のフォローの数（チームメンバー自身を除く）。
- チームメンバー自身（自分のチームの発信者）の操作は、数えない。
- 退会したユーザーの記録は、ユーザーと一緒に消える。数え終えた合計は、そのまま残す。

> <kbd>異常系</kbd>
>
> - 記録を送れない（アプリ）　→　捨てる。送り直さない（数が少し減ることを受け入れる）

#### 4.2.2 数の表示

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者のチームメンバーに、数（4.2.1）を、配信ごと（予定ごと）と、直近30日の合計・日ごとの推移で見せる |
| 事前条件 | 自分のチームの発信者がある |
| 関連画面 | 発信者メニュー、届いた数（画面定義書（設定・発信者）2.3.16） |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 見られるのは、その発信者のチームメンバーだけ。ファンには見せない。
- 予定が見られた数は、予定ごとの数も出す（終わった予定も、期間の中なら出す）。
- 期間は、配信ごと（1回の配信・予定ごとの「届けた・来た」）と、直近30日の合計（2026-11-15 本人）。
- 数は丸めない。1人からそのまま出す。出すのは合計だけで、誰かは出さない（2026-11-15 本人）。
- 数の画面（届いた数。画面定義書（設定・発信者）2.3.16）は、発信者メニューのプロフィールカードの要約（「直近30日で {N}人に通知を届けました」）から開く（2026-11-19 本人）。見た目と入口は、本人の指示で Figma を飛ばし、今の画面にそろえた仮の決め（2026-11-16）。
- 直近30日は、日本時間の昨日までの30日（日ごとの合計は次の日の0時5分にできるため）。30日の合計の人数は、日ごとの人数を足したもの（同じ人が2日来れば2と数える）。

> <kbd>異常系</kbd>
>
> - 読めない　→　失敗を知らせ、「もう一度試す」を出す

#### 4.2.3 投稿が見られた数

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 追星の中で、発信者の投稿（YouTube・Instagram・X）が開かれた回数と、画面に出た回数を、日ごとに数える。届いた数の画面で、直近30日の合計を見せる（2026-11-19 本人） |
| 事前条件 | なし |
| 関連画面 | 数えるのは、ホーム・発信者ページ・スケジュール（画面定義書（ファン向け））と投稿ビューア（2.4.3）。見せるのは、届いた数（画面定義書（設定・発信者）2.3.16） |
| 入力項目・バリデーション | なし |

<kbd>数えるもの</kbd>

| 数 | 数え方 |
| --- | --- |
| 投稿を開いた数 | 投稿ビューアで投稿が出た回数。押して開いた投稿に加え、ビューアの中で上下にスワイプして出た投稿も数える（2026-11-19 本人）。1回ビューアを開いている間、同じ投稿は1回 |
| 投稿が表示された数 | ホーム・発信者ページ（配信中を含む）の投稿のカードと、スケジュールの投稿のまとまりの行が、画面に出た回数（インプレッション） |

- 数えるのは回数だけ。誰が見たかの記録は、一時的なものも含めて持たない（リンク集の押された数（4.6.3）と同じ考え方。2026-11-19 本人）。表には「発信者・投稿・日・回数」だけを持つ。
- その発信者のチームメンバー自身が見た分は、数えない（アプリから送らず、サーバーでも外す）。サインインしていない呼び出しは数えない。
- 投稿ビューアの中・固定ビューア・発信者メニューの投稿の管理は、表示された数に入れない。
- 表示された数は回数が多くなるので、次の決まりで数える（2026-11-19 本人）。
  - カードの面積の半分以上が、続けて1秒以上画面に出たときだけ数える。速くスクロールして流れたものは数えない。
  - 同じ投稿は、アプリを起動してから1回だけ数える（アプリの中のメモリで覚え、アプリを終了すると忘れる）。
  - アプリの中でためて、30秒ごとにまとめて1回送る。50件たまったとき・アプリが裏に回ったときにも送る。開いた数も同じ送信に入れる。
- 1回の送信は50件まで。1件の回数は、開いた数20・表示された数1までにして、大きく盛れないようにする。追星にない投稿（消えた投稿など）は数えない。
- 日の区切りは日本時間の0時。数は丸めない。
- 投稿は保持の決まり（90日など）で消えるので、数は投稿と切り離して残す。90日より前の数は、毎日の集計（4.2.1）のときに消す。
- 投稿ごとの数は出さない。合計だけ（2026-11-19 本人）。発信者メニューのプロフィールカードの要約にも出さない。

<kbd>補足・実装メモ</kbd>

- 届いた数の画面に、ほかの数と同じ期間（日本時間の昨日までの30日）の合計を、「投稿」の見出しの下に2行で出す。
- 画面に出たかの判定は、パッケージ `visibility_detector` を使う（検証結果 tech-risks）。

> <kbd>異常系</kbd>
>
> - 記録を送れない（アプリ）　→　捨てる。送り直さない（数が少し減ることを受け入れる）

### 4.3 リンクの共有

#### 4.3.1 共有のリンクとページ

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者ごとに、追星の外に貼れるリンクを持つ。リンクを開くと共有のページを通り、アプリが無い人は App Store へ、アプリがある人は発信者ページへ行く |
| 事前条件 | 発信者が、ファンに見せる状態（確認済みのアカウントがあり、停止中でも、オーナーが退会した発信者でもない） |
| 関連画面 | 共有のページ（ウェブ） |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- リンクは `https://oiboshi.perrii.app/c/{発信者 ID}` にする（2026-11-15 本人）。
- 共有のページは、公開用のウェブサイト（公開サイトのリポジトリ（別管理） の `oiboshi/`、Cloudflare Workers）で出す。発信者の名前とアイコンは、ファンに見せてよい公開の値だけを、Supabase から読む。
- OGP（2026-11-19 本人。リンク集のページとして、Linktree の出し方にならう）：タイトルは「{発信者の名前}｜追星」、説明はプロフィール文の1行目（80文字まで。超えたら「…」）、プロフィール文が空なら「{発信者の名前}のリンク集」。画像は発信者のアイコンで、X には `summary`（小さい正方形）のカードで出す。カバーで大きなカードにはしない。画像は新しく作らない。
- ページの中身（2026-11-19 本人。よくあるリンク集の並べ方に寄せる。Linktree のロゴ・名前・色は使わない）：真ん中に丸いアイコン、名前、プロフィール文（改行もそのまま）。その下に、リンク集（4.6.2）の横幅いっぱいの角の丸いボタンを縦に並べる。追星への入口（「追星アプリなら、{名前}の配信が始まったら通知で知らせます。」、小さめの「App Store で入れる」、「アプリで開く」（アプリ内のブラウザで開いたとき用））は、線で区切ったページの下に控えめに置く。リンクが1件もなければ、「App Store で入れる」を大きく出す。SNS の一覧や配信中は出さない。QR は出さない。
- 「アプリで開く」の行き先は、カスタムの URL スキーム `oiboshi://c/{発信者 ID}` にする。表示中のページと同じドメインへのリンクでは、iOS がアプリを開かないため（tech-risks 2.30）。URL スキームは Safari でもアプリ内のブラウザでも働くので、同じボタンにする。Safari には、Smart App Banner（`apple-itunes-app`）も出す。
- 「App Store で入れる」を押したとき、引き継ぎ（4.3.4）のために、リンクをクリップボードに写してから、App Store を開く。
- Universal Link のために、`/.well-known/apple-app-site-association` を同じドメインで出し、`/c/*` をアプリに渡す。
- 外部のサービス（短縮 URL・ディープリンクのサービス）は使わない。

> <kbd>異常系</kbd>
>
> - 発信者がない・ファンに見せない状態　→　「見つかりませんでした」と、追星の App Store への案内だけを出す。OGP に発信者の名前とアイコンを出さない

#### 4.3.2 リンクの共有

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者のチームメンバーとファンが、発信者の共有のリンクを、OS の共有シートで共有する |
| 事前条件 | その発信者が、ファンに見せる状態 |
| 関連画面 | 発信者メニュー、発信者ページ、「リンクを共有」の画面 |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 共有シートに渡すのは、誘う用のリンク（4.3.6）と、短い文。どこから共有しても、リンクと QR は誘う用にする（2026-11-19 本人：「全部『追星に誘う』の機能にしていいよ。どの共有ルートでも」）。文は、ファンなら「{名前}の配信と予定を、追星で追えます」、発信者の側（発信者メニューの「追星に誘う」・自分の発信者ページ・リンク集の「共有」）なら「追星で私の配信・予定を追いかけてね」。
- 「リンクを共有」の置き場は、オーナーが開いた自分の発信者ページ・ファンが開いた発信者ページ（2026-11-15 本人）。ファンも同じリンクを共有できる。発信者メニューの「リンクを共有」は、「追星に誘う」と同じになったので消した（2026-11-19 本人）。
- 押すと「リンクを共有」の画面（画面定義書（ファン向け）2.4.4）を開き、リンクと QR（4.3.5）を出す。そこから共有シートに渡す。見た目は、本人の指示で Figma を飛ばし、今の画面にそろえた仮の決め（2026-11-16）。

> <kbd>異常系</kbd>
>
> - 発信者がファンに見せない状態　→　共有を出さず、理由（確認済みのアカウントがない・停止中）を出す

#### 4.3.3 アプリで開く

| 項目 | 内容 |
| --- | --- |
| 機能概要 | アプリが入っている端末で共有のリンクを開くと、アプリで、その発信者のページを開く |
| 事前条件 | アプリが入っている |
| 関連画面 | 発信者ページ |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- iOS の Universal Link（Associated Domains、`applinks:oiboshi.perrii.app`）で受ける。共有のページの「アプリで開く」から来る `oiboshi://c/{発信者 ID}` も、同じに扱う（tech-risks 2.30）。
- 開くのは、推しのタブの発信者ページ。フォローは、ファンが押す（自動ではフォローにしない）。
- 初回起動が済んでいなければ、済んでから開く（通知を押したとき（機能仕様書 4.3.3）と同じ）。
- X・LINE などのアプリ内のブラウザでは、Universal Link が働かず、共有のページが開くことがある。そのときは、ページの「アプリで開く」で開く。

> <kbd>異常系</kbd>
>
> - 発信者がない・ファンに見せない状態　→　ホームを開き、「見つかりませんでした」と知らせる

#### 4.3.4 入れたあとの引き継ぎ

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 共有のページを通ってアプリを入れた人が、初めてアプリを開いたとき、その発信者のページを出す |
| 事前条件 | 初回起動。共有のページで「App Store で入れる」を押している |
| 関連画面 | 初回起動の画面、発信者ページ |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 外部のサービスは使わず、クリップボードで引き継ぐ。共有のページが写したリンクを、初回起動で読む。
- 読む前に、クリップボードに URL らしいものがあるかを、中身を読まずに確かめる（iOS の `UIPasteboard.detectedPatterns`。確認は出ない）。URL らしいものがなければ、読まない。
- URL らしいものがあれば読む。このとき iOS の「ペーストを許可」の確認が出る。許可されなければ、引き継がない。確認を避ける貼り付けボタンの形は採らない（2026-11-15 本人。tech-risks 2.31）。
- 読んだ URL が共有のリンクの形のときだけ、その発信者を引き継ぐ。ほかの URL は使わず、残さない。
- 読むのは、初回起動の1回だけ。
- 出す時点は、「はじめる」（機能仕様書 4.1.2）のあと、推しを選ぶの前。いつもの発信者ページをそのまま開き、初回専用の画面は作らない。戻ると推しを選ぶ画面に進む（2026-11-15 本人）。フォローは、ファンが押す。
- 誘う用のリンク（`?invite=1`。4.3.6）を引き継いだときだけ、発信者ページを出す前に、その発信者をフォローする（2026-11-18 本人）。同意は、誘う用のページの「入れて開くと、{名前}をフォローした状態で始まります」と、「はじめる」を押すことで取る。アプリでは確認のダイアログを出さず、発信者ページでスナックバー「{名前}をフォローしました」を出す。推しごとの通知は、ふつうのフォローと同じくオン。端末の通知の許可は、今までどおり「通知の説明」で聞く。フォローできなくても、ページは出す（ファンが押せる）。
- 自動のフォローも、フォロワーの増え方（4.2.1）に数える。

> <kbd>異常系</kbd>
>
> - 引き継いだ発信者がない・ファンに見せない状態　→　引き継がず、ふつうの初回起動を続ける

#### 4.3.5 QR

| 機能概要 | 共有のリンクを QR で出す |
| 事前条件 | 4.3.2 と同じ |

| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- QR の中身は、誘う用のリンク（4.3.6）にする（2026-11-19 本人）。
- QR は、アプリの中で作る（外部のサービスは使わない）。
- 出すのは、「リンクを共有」の画面（リンクと一緒に）だけ（2026-11-15 本人。週間の告知画像の中にも出していたが、2026-11-19 本人の決めで入れなくなった）。発信者ページには出さない。「リンクを共有」の画面から、QR だけを画像（1024×1024 の PNG）にして共有シートに渡せる。「画像を保存」で写真に保存でき、配信画面や会場にも置ける（2026-11-16 本人）。

#### 4.3.6 追星に誘う

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者が、ファンに追星を入れてもらうためのリンクを共有する。開いた人には、誘う文言と大きな App Store のボタンを先に出し、入れて開いた人は、その発信者をフォローした状態で始まる |
| 事前条件 | 4.3.2 と同じ（発信者がファンに見せる状態） |
| 関連画面 | 発信者メニュー、「追星に誘う」の画面（画面定義書（ファン向け）2.4.4。「リンクを共有」の画面の誘う用）、共有のページ（ウェブ） |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 「追星に誘う」の画面の置き場は、発信者メニューのプロフィールカードの共有のボタン（もとは「シェア」の行）と、自分の発信者ページのメニューの「リンクを共有」（2026-11-18・11-19 本人）。
- アプリから共有するリンクは、どこから共有しても誘う用にする（2026-11-19 本人：「全部『追星に誘う』の機能にしていいよ。どの共有ルートでも」）。ファンが発信者ページから共有するとき（4.3.2）・リンク集の「共有」（4.6.1）・QR（4.3.5）も同じ（週間の告知画像には、2026-11-19 から QR を入れない）。
- 誘う用のリンクは、共有のリンク（4.3.1）に誘う用の印を付けたもの：`https://oiboshi.perrii.app/c/{発信者 ID}?invite=1`。追星を入れている人が開いたときは、印のない共有のリンクと同じく、アプリで発信者ページを開く（4.3.3）。
- 共有シートに渡す文は、誘う文を最初から入れる：「追星で私の配信・予定を追いかけてね」と、誘う用のリンク。
- QR も、誘う用のリンクにする。
- 共有のページ（4.3.1）は、`invite=1` のときだけ、先頭に誘う文言（「追星で{名前}を追いかけよう」）と大きな「App Store で入れる」を出す。ボタンの下に「入れて開くと、{名前}をフォローした状態で始まります」と書く。その下は、ふつうの共有のページと同じ（アイコン・名前・プロフィール文・リンク集・アプリで開く）。ただし、App Store のボタンを2つ並べないよう、下のふつうの「App Store で入れる」とその注記は出さない。OGP は、ふつうの共有のページと同じ。
- 誘う用のページの「App Store で入れる」は、誘う用のリンク（印つき）をクリップボードに写す（引き継ぎ。4.3.4）。
- 入れて初めて開いたときは、引き継ぎ（4.3.4）で、その発信者をフォローしてから、発信者ページを出す（2026-11-18 本人）。
- 見た目と文言は、作ったものを本人が見て直す前提（2026-11-18 本人）。

> <kbd>異常系</kbd>
>
> - 発信者がファンに見せない状態　→　4.3.2 と同じ（共有を出さず、理由を出す）

### 4.4 告知の画像

#### 4.4.1 週間の告知画像

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者のチームメンバーが、自分の発信者の1週間の予定から、告知の画像を作り、OS の共有シートで共有する |
| 事前条件 | 自分のチームの発信者がある |
| 関連画面 | 発信者メニュー、週間の告知画像（画面定義書（設定・発信者）2.3.15） |
| 入力項目・バリデーション | 週（今週・来週）、テンプレ、画像（任意。端末の写真から1枚） |

<kbd>補足・実装メモ</kbd>

- 載せる予定は、その週の、その発信者の予定（予約とイベントの公演。機能仕様書 4.5.3 のファンに見せる予定と同じもの）。
- 週は、月曜から日曜（2026-11-15 本人。区切りは端末の時刻）。
- 画像に入れるもの：発信者の画像（アイコンか、選んだ画像）と名前、週の日付、日ごとの予定（時刻・サービスかイベント・タイトル）、追星のロゴ。追星の QR とリンクの文字は入れない（2026-11-19 本人：「画像内に追星の URL やコードは不要です」）。予定ごとのリンクと誘う用のリンクは、一緒に共有する文に入れる（下）。
- 画像は、サーバー（Supabase Edge Functions の `announce-image`）で作る（2026-11-19 本人「v1.1.0 から移す」「Supabase で試す」）。画像は「情報を流し込むだけ」の機能で、テンプレの追加や直しを、アプリの更新なしで出すため。細かな編集の機能は持たない。大きさは、X に貼る横長 16:9（1200×675）。作り方の検証は tech-risks 2.39。
  - アプリは、ログインしたまま関数を呼ぶ（発信者・週・テンプレを渡す）。関数は、呼んだ人がその発信者のチームメンバーかを確かめてから、サーバーで予定・名前・画像を読む（匿名では作れない。ファンに見せない発信者でも、チームメンバーなら作れる）。
  - 予定を選ぶ決まりは、アプリの予定の読み込みと同じ（この版で出さない SNS の予定は除く。始まった配信の予約は、実績と二重に出さない。実績は載せない）。
  - 週の区切りと時刻は、端末の時刻（アプリが、端末の時差を渡す）。
- テンプレ（2026-11-19 本人）：画像の見た目は、テンプレから選ぶ。テンプレは、サーバー（関数の中のテンプレの定義と一覧）だけで足せ、アプリの更新は要らない。
  - 一覧：ID・表示名・サムネイル（見本のデータで作っておいた小さな画像。関数に入れておく）・並び順・出すか。出さないテンプレは一覧に入れない。テンプレを足すときは、定義を書き、サムネイルを作り直して（`deno task announce-thumbnails`）、関数を出し直す。
  - 知らない ID や消したテンプレが来たら、既定のテンプレで作る。
  - リリースのときのテンプレは1つ（`spotlight`。表示名「スポットライト」）：発信者の画像を、画像の高さいっぱいの正方形で左の端に寄せて置き、右の端を背景へなめらかにぼかして溶かす。背景は、同じ画像を強くぼかして暗くした色のグラデーション。日ごとの予定は、右側に白い面で浮かせて置く（2026-11-19 本人「これで作って」）。
- 発信者が選んだ画像（2026-11-19 本人）：アイコンの代わりに、端末の写真から1枚を選んで使える。発信者ごとに1枚で、次の週もそのまま使う。変える・アイコンに戻すは、いつでもできる。選んでいなければアイコン。
  - 切り抜きは、自動で真ん中（テンプレの置き方のまま）。位置の調整は持たない。
  - どのテンプレでも、同じ画像を使う。
  - アプリで長辺 1000 に縮めてから（画像を作る関数が読む手間を減らすため。tech-risks 2.39）、発信者の画像の置き場（`creator-images` の `{発信者 ID}/announce.jpg`。アイコン・カバーと同じ。そのチームのメンバーだけが書ける）に上げる。画像を作る関数は、公開の URL ではなく Storage から直接読む。
  - 選んだ画像は、アプリの中では誰にも見せない（出るのは、発信者が共有した先の SNS の投稿だけ）。そのため、追星の通報（機能仕様書 4.2.7）の入口は無く、通報の対象に入れない。権利のない画像などは、利用規約の禁止事項（他人の権利の侵害）に当たり、権利者からの申し立ては問い合わせの窓口で受けて、運営が消す（2026-11-19 確かめ）。
  - プライバシーポリシーに、この画像と、画像の文字の形を取る Google Fonts を足す（公開サイトのリポジトリ（別管理） の PR で下書き）。ストアのプライバシーの回答は、今の「写真またはビデオ」（発信者のアイコンとカバー）に入るので、新しい項目は要らない。
- 名前の絵文字は、今はフォントに無いので落として描く（Twemoji を読むかは、あとで決める。tech-risks 2.39）。
- 予定がない週も作れる（「今週の予定はまだありません」）。
- 共有のとき、画像と一緒に文を渡す（2026-11-19 本人：「告知画像って、シェアする時に、全部の URL をテキストとして投稿できないかな？」「予定ごとの URL ＋ 誘う用」）。共有のボタンを1回押すと、画像と文が一緒に共有シートに出る（画像とリンクが一度で共有できる、を見せるため。2026-11-19 本人）。
  - 文の形：1行目に見出し「{名前}の週間の予定（11/16–11/22）」。続けて、予定ごとに1行「11/19(木) 22:00 題名 URL」（題名は24文字まで、超えたら「…」）。空行のあと「▼追星で通知を受け取る」と、誘う用のリンク（4.3.6）。
  - 文に入れるリンク（予定ごとのリンクと誘う用のリンク）は、全部、追星の短い URL（4.4.2）にする（2026-11-19 本人「これで作って」）。下の「予定の URL」は、短い URL の転送先。
  - 予定の URL：YouTube の取った予約は予約の動画のページ（`https://youtu.be/{動画の ID}`）、Twitch・ツイキャスの予約は、チャンネルのページ。イベントの公演は、リンク（チケットなど）。リンクが広告（PR）なら、公演のページにする（文に PR と書けないため）。
  - リンクの無い予定は、文に入れない（画像に全部載っていて、文はリンクを渡すためのもの）。前の行と同じ URL（同じチャンネルの配信が続くとき）は、2回目から URL を付けない。
  - 長さは、X の1投稿（280。日本語などの全角は1文字を2、URL は1本 23 と数える）に収める。共有シートでは行き先が分からないので、一番短い X に合わせた。入りきらない予定は「ほか N 件」にまとめ、誘う用のリンクは必ず残す。日本語の題名だと、1つの文に入る予定はおよそ3〜4件。
  - Instagram は、共有シートの文が投稿に入らない。画面に文の見本と「文をコピー」を置き、キャプションに貼れるようにした。


#### 4.4.2 告知のリンクの短い URL

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 週間の告知画像と一緒に共有する文のリンクを、全部、追星の短い URL にする。押されたら元の URL へそのまま転送し、押された数を数える |
| 事前条件 | 作るのは、その発信者のチームメンバー（4.4.1 と同じ） |
| 関連画面 | 週間の告知画像（画面定義書（設定・発信者）2.3.15）、短い URL の転送（ウェブ。画面は無い） |
| 入力項目・バリデーション | なし（共有の文を作るときに、アプリが自動で作る） |

<kbd>補足・実装メモ</kbd>

- 2026-11-19 本人「これで作って」。対象は、共有の文の予定ごとのリンクと、誘う用のリンク（4.3.6）の全部。
- 形：`https://oiboshi.perrii.app/s/{ID}`。ID は、推測されにくい12文字（英大文字・小文字・数字・`-`・`_`。72ビットの乱数）。
- 押されたら、共有のページと同じ Worker が、元の URL へ HTTP の転送（302）でそのまま送る。中継のページは挟まない（X などがカードを作るときに転送先をたどって、元のサイトのカードが出るように）。誘う用のリンクなら、転送先は今の `?invite=1` の付いた共有のページ。
- 作るのは、共有の文を作るとき（画面を開いて、週を選んだとき）。同じ発信者で同じ行き先なら、同じ短い URL を使い回す（週を変えても、何度共有しても同じ）。
- 踏み台（外の任意の URL へ飛ばすこと）に使われないよう、登録できる行き先は、追星が持っているものだけにする：その発信者の誘う用のリンク、予定（取った予約・イベントの公演）のリンク（YouTube の予約の動画のページ・チケットなどのリンク・公演のページ）、つないだ SNS のチャンネルのページ。ほかの URL は短い URL を作らない（アプリは元の URL のまま使う）。
- 作れないとき（通信の失敗など）は、短くしない元の URL で文を作る（共有は止めない）。
- 押された数：転送するたびに1と数える。誰が押したかの記録は持たない（4.6.3 と同じ）。X・Facebook・LINE・Slack・Discord などがカードを作るための見回り（クローラー。User-Agent で見分ける）は、数えずに転送する。
- 数の見せ方（2026-11-19 本人「これで作って」。リンク集の「押された数」4.6.3 に合わせる）：
  - 見るのは、その発信者のチームメンバーだけ。ファンには見せない。
  - 週間の告知画像の画面の、「一緒に共有する文」の下に「リンクが押された数」を置き、その週の文に入っているリンクを1行ずつ並べる（予定は日付と題名、誘う用のリンクは「追星に誘うリンク」と、押された数）。
  - 数は、短い URL を作ってからの合計を1つの数で出す。日ごとの数は持たない。誘う用のリンクは、どの週も同じ短い URL なので、週をまたいだ合計になる（注記で知らせる）。
  - 読めないときは、この区画を出さない（画像と文の共有は止めない）。
- 予定や SNS のつなぎを消しても、作った短い URL は残す（貼った投稿のリンクを切らさないため）。発信者を消すと、一緒に消える。

> <kbd>異常系</kbd>
>
> - 無い ID・形の違う ID　→　404（共有のページの「見つかりませんでした」と同じ）
> - 数えられない　→　捨てる。転送はする

### 4.5 追いたい

#### 4.5.1 申告と追いたい

| 項目 | 内容 |
| --- | --- |
| 機能概要 | ファンが、追星に未登録の人を、SNS の URL か ID で申告して、「追いたい」を押す |
| 事前条件 | なし（匿名でよい） |
| 関連画面 | 推しを探す、追いたい（画面定義書 2.3.4） |
| 入力項目・バリデーション | SNS の URL か ID。SNS の種別（URL から分かれば自動） |

<kbd>補足・実装メモ</kbd>

- 申告できる SNS は、追星が連携できる SNS（機能仕様書 4.6.2）。
- 追星が持つのは、SNS の種別・ID・押した人数だけ。他人の名前やアイコンは、取らないし出さない。SNS の API でアカウントがあるかを確かめることもしない。外部の名前の検索もしない。
- 押した人数を数え、登録したときに知らせる（4.5.2）ために、誰が押したかを持つ。誰が押したかは、ほかのファンにも、発信者にも出さない。
- URL は、SNS ごとの形から ID を取り出して、同じ形にそろえる（小文字にする、`@` を外すなど）。形が分からなければ、受け付けない。
- 読む URL は、アカウントのページだけ（YouTube は `/@ハンドル` と `/channel/チャンネル ID`。X・Instagram・Twitch・ツイキャスは、パスの先頭のユーザー名）。動画・投稿のページ（YouTube の `watch`・`youtu.be` など）や、YouTube の古い形（`/c/`・`/user/`）は、チャンネルが決まらないので受け付けない。ID だけを入れたときは、SNS を選んでもらう。
- YouTube は、チャンネル ID とハンドルを別のものとして持つ（SNS の API で結び付けないため）。どちらでも、確認済みのアカウント（チャンネル ID と、ハンドル）と突き合わせる。
- 申告した ID が、どれかの発信者の確認済みのアカウントなら、追いたいにせず、その発信者を出す（推しの検索、機能仕様書 4.2.2 と同じ）。
- 未登録のアカウントは、本人確認なしとして扱う。登録済みの発信者と混ぜて見せない（推しを探すの一覧・検索・おすすめに出さない）。出すのは、追いたいの一覧だけ。
- 追いたいの一覧には、自分が押したものを、SNS の種別・ID・押した人数で出す。押した人数は、ファンにも見せる（「◯人が追いたい」。2026-11-15 本人）。誰が押したかは出さない。一覧は、推しを探すから入る「追いたい」の画面（画面定義書 2.3.4）に出す。
- 追いたいは、取り消せる。
- 申告された ID を消すのは、その人が登録してアカウントが確認済みになったとき（4.5.2）と、押した人が全員いなくなったとき（取り消し・退会）だけ。期限では消さない（2026-11-15 本人）。
- 1人が1日に申告できるのは、10件まで（2026-11-15 本人）。サーバーで、直近24時間に押した数で数える。押したものをもう一度押しても数えない。

> <kbd>異常系</kbd>
>
> - URL・ID の形が分からない　→　「この形の URL は読めません」と出す
> - 上限を超えた　→　「今日はこれ以上申告できません」と出す

#### 4.5.2 登録したときの通知と自動のフォロー

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 追いたいで申告された人が、追星に発信者として登録し、そのアカウントを確認済みにしたら、押したファンに知らせ、自動でフォローにする |
| 事前条件 | 申告された SNS の種別と ID が、発信者の確認済みのアカウントと一致した |
| 関連画面 | 発信者ページ |
| 入力項目・バリデーション | なし |

<kbd>処理フロー</kbd>

1. アカウント連携（機能仕様書 4.6.2）で、アカウントが確認済みになる。
2. サーバーが、5分ごとに、見せる発信者の確認済みのアカウントと、未登録のアカウントを突き合わせる（比べ方は、申告のとき（4.5.1）と同じ）。一致があるときだけ、通知の関数を呼ぶ。
3. 一致したら、押したファンのそれぞれを、その発信者のフォローにする（推しごとの通知は、フォローしたときの初期と同じオン。配信開始の通知と予定の事前通知も届く）。
4. 新しくフォローにしたファンに、プッシュ通知で知らせる。押すと、その発信者のページを開く。
5. その未登録のアカウントと、押した記録を消す（追星が持つ申告の ID は、ここと、押した人が全員いなくなったときに消える。4.5.1）。

<kbd>補足・実装メモ</kbd>

- 発信者が、ファンに見せる状態になったときだけ行う。停止中・オーナーが退会した発信者では行わず、記録を残す。
- 全体のスイッチがオフのファンにも、フォローにはする（通知だけ送らない）。
- そのファンが、その発信者を表示しない（機能仕様書 4.2.6）にしていれば、フォローにせず、記録だけを消す。
- 自動のフォローで増えたフォロワーも、フォロワーの増え方（4.2.1）に数える。
- もうフォローしているファンには、通知しない（フォローしましたと知らせることにならないため）。その発信者のオーナー自身は、フォローにしない。
- フォローと記録の削除は、通知を送る前に済ませる。同じ人に二度は知らせない。
- 通知の文言は、配信開始の通知と同じく、送り先の端末の言語（日本語・英語）で作る（i18n設計書 6.5）。文言は、日本語が見出し「{発信者の名前}が追星に来ました！」・本文「追いたいが届きました。これからは配信も予定もお知らせします」（2026-11-15 本人）。英語は見出し「{name} is now on Oiboshi!」・本文「Your wish came true. We'll now let you know about their streams and schedules.」。
- 通知のデータ：`type` は `want_arrival`、`creator_id` は発信者の ID。押したときに開く画面は、アプリのルーティング（共有のリンクの作業）で受け持つ。届かないまま1日を過ぎた通知は捨てる。

> <kbd>異常系</kbd>
>
> - 通知を送れない　→　フォローにはして、記録は消す（送り直さない）。ログに書く

#### 4.5.3 運営の声かけ

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 運営が、未登録のアカウントを押した人数の多い順に見て、その人に追星への登録を勧める |
| 事前条件 | 運営（SQL で見る） |
| 関連画面 | なし |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 運営は、SQL（ビュー `wanted_account_ranking`。データ設計書 3.2.4）で、SNS の種別・ID・押した人数を、多い順に見る。手順は、環境構成 9章。
- 声をかけるのは、その SNS の DM か、その人の問い合わせフォーム。メールは使わない（SNS の API からメールアドレスは取れず、宣伝のメールは特定電子メール法で、相手の同意が要るため）。
- 声をかけたかは、運営が SQL で印を付ける（同じ人に何度も声をかけないため）。押した人が全員いなくなったら、印もアカウントと一緒に消える（4.5.1）。

### 4.6 リンク集

発信者が、好きなリンク（題名と URL）を並べて、追星の発信者ページと公開のページ（共有のページ）に、ボタンで出す機能（Linktree のようなもの）。発信者に追星を使ってもらう理由を増やすために、v1.1.0 に入れる（2026-11-18 本人。決定事項 1章）。数の上限・題名の長さ・押された数の数え方・短縮 URL の一覧・ウェブに通報を置かないことも、2026-11-18 に本人が決めた。見た目の着せ替え、日ごとのグラフ、リンクの画像は入れない。

#### 4.6.1 リンクの登録

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者のオーナーが、リンクを足し、題名と URL を直し、並べ替え、消す |
| 事前条件 | 発信者として登録中で、その発信者のオーナー |
| 関連画面 | 発信者メニュー、リンク集（画面定義書（設定・発信者）2.3.17）、リンク集の編集（2.3.19）、リンクの追加・編集（シート。2.3.18） |
| 入力項目・バリデーション | 題名（必須、1〜30文字。見た目の1文字で数える。前後の空白は除く）、URL（必須、`https://` で始まる URL。2000文字まで。短縮 URL は受け付けない） |

<kbd>補足・実装メモ</kbd>

- 触れるのは、その発信者のオーナーだけ（データベースの RLS で守る）。
- 1つの発信者に、10件まで（2026-11-18 本人。Linktree は上限なし。発信者ページで SNS の下に並べるので、長くなりすぎないように）。
- 並びは、オーナーが決める。足したリンクは、いちばん下に入る。並べ替えは、つかんで動かす。
- 停止中（機能仕様書 4.6.7）でも、オーナーは編集できる（ファンには出ない）。
- リンク集の画面は、開いた最初の画面（着地の画面）と、編集の画面に分ける（2026-11-19 本人）。着地の画面に出すのは、リンク集のページの見本（公開のページ（4.3.1）と同じ見た目：丸いアイコン・名前・プロフィール文・リンクのボタン。公開のページは読み込まず、アプリの持つデータから組み立てる。2026-11-19 本人）、「編集」「共有」のボタン、リンクごとの押された数（4.6.3。読むだけ）の3つだけ。「追加」・説明の文・URL の表示は置かない。足す・直す・並べ替え・消すは、「編集」で開く編集の画面で行う。
- 「共有」は、公開のページの誘う用のリンク（`oiboshi.perrii.app/c/{ID}?invite=1`。4.3.6）を、「追星に誘う」と同じ文で共有シートに渡す（2026-11-19 本人。どの共有も誘う用にした）。共有のしかたは「リンクを共有」（4.3.2）と同じで、ファンに見せない状態の発信者は共有しない。コピーは、共有シートから行う。
- 危ないリンクの扱いは、4.6.4。

> <kbd>異常系</kbd>
>
> - 題名・URL の形が違う　→　保存せず、どこが違うかを出す
> - 短縮 URL　→　「短縮 URL は使えません。行き先の URL をそのまま入れてください」と出す
> - 10件を超える　→　「追加」を押せない。「リンクは10件までです」と出す
> - 保存・並べ替え・削除に失敗　→　失敗を知らせ、保存されている内容を読み直して出す

#### 4.6.2 リンクの表示

| 項目 | 内容 |
| --- | --- |
| 機能概要 | リンク集を、アプリの発信者ページと、公開のページ（`oiboshi.perrii.app/c/{発信者 ID}`）に、ボタンで並べる |
| 事前条件 | 発信者が、ファンに見せる状態（4.3.1 と同じ） |
| 関連画面 | 発信者ページ（画面定義書（ファン向け）2.4.1）、リンクを開く前の確かめ（ダイアログ。2.4.1 の中）、共有のページ（ウェブ） |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- アプリ：発信者ページの、つないだ SNS（合計フォロワー数と SNS のチップ）の下に、リンクを1件1つのボタンで、縦に並べる。リンクが1件もなければ、何も出さない。追星に誘うリンク（4.6.6）は出さない。つないだ SNS のアカウントのページを指すリンク（自動で入れた SNS のリンク（4.6.5）を含む）は出さない。SNS ごとのフォロワー数の所（押すとその SNS を開く）で足りるため（2026-11-19 本人）。公開のページには、SNS のリンクも並べる（Linktree と同じ）。
- アプリ：押すと、開く前の確かめ（行き先のドメインを出す。イベントのリンクと同じ。機能仕様書 4.5.3）を出し、「開く」で外部のブラウザで開く。確かめのダイアログに「通報する」を置く（4.6.4）。
- 公開のページ：名前・アイコン・案内の下に、同じくボタンで並べる。ボタンの行き先は、公開のページの中の数えるための URL（`/c/{発信者 ID}/l/{リンク ID}`）で、そこで数えてから（4.6.3）、リンク先へ送る。リンクが1件もなければ、何も出さない。
- 公開のページで読めるのは、ファンに見せる状態の発信者のリンクだけ（共有のページの発信者と同じ条件。データ設計書 3.3 `shared_creator_links`）。
- `https://` で始まらないリンクは、出さない・開かない（古い値や、運営が直した値の守り）。

> <kbd>異常系</kbd>
>
> - リンクを読めない（アプリ）　→　リンクの欄だけを出さない。ページのほかの部分は出す
> - 数える URL のリンクがない・ファンに見せない（ウェブ）　→　共有のページの「見つかりませんでした」と同じページを出す

#### 4.6.3 押された数

| 項目 | 内容 |
| --- | --- |
| 機能概要 | リンクごとに押された回数を数え、その発信者のオーナーだけに見せる |
| 事前条件 | 見るのは、その発信者のオーナー |
| 関連画面 | リンク集（画面定義書（設定・発信者）2.3.17）、リンク集の編集（2.3.19） |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 数えるのは、押された回数（2026-11-18 本人）。同じ人が何回押しても、そのたびに1と数える。誰が押したかの記録は持たない（ユーザーを含む記録を増やさないため）。
- アプリで押したもの：開く前の確かめで「開く」を押したときに数える。その発信者のオーナー自身が押した分は数えない。
- 公開のページで押したもの：数えるための URL を開いたときに数える。誰か分からないので、すべて数える。
- アプリとウェブの合計を、1つの数で出す（分けない）。
- 期間は、リンクを作ってからの合計だけ。日ごとの数は持たない（グラフは入れない）。URL を書き換えたら0に戻す（ほかの行き先の数が混ざらないように）。題名だけを変えたときは残す。
- ファンには見せない。リンクを消すと、数も消える。
- 見る所は、リンク集の着地の画面（アイコン・題名・数）と、編集の画面（一覧の行の右）。数え方の注記は、編集の画面の下に置く（2026-11-19 本人）。
- 着地の画面の一覧は、編集の画面と同じく、リンク集に登録した順に並べる（2026-11-19 本人：「設定と『押された数』は並び合ってるわ」）。行の左に、見本のボタンと同じアイコンを付ける（4.6.7）。

> <kbd>異常系</kbd>
>
> - 数えられない　→　捨てる。送り直さない（リンクは開く）

#### 4.6.4 危ないリンクの対策

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 危ないリンクを入れさせない・見つけたら止める |
| 事前条件 | なし |
| 関連画面 | リンクの追加・編集（シート）、リンクを開く前の確かめ（ダイアログ）、通報（シート） |
| 入力項目・バリデーション | 4.6.1 |

<kbd>補足・実装メモ</kbd>

- `https://` で始まる URL だけを受け付ける。データベースでも確かめる（アプリを通さない書き込みの守り）。
- 短縮 URL（行き先が見えない URL）は断る。断るドメインは、データベースの一覧（データ設計書 3.1.33 `blocked_link_hosts`）に持ち、運営が SQL で足す（アプリを出し直さずに増やせる）。最初の一覧は `bit.ly`・`t.co`・`tinyurl.com`・`goo.gl`・`ow.ly`・`is.gd`・`buff.ly`・`cutt.ly`・`x.gd`・`t.ly`・`shorturl.at`・`rebrand.ly`・`amzn.to`・`tiny.cc`・`v.gd`・`lnkd.in`・`dlvr.it`・`s.id`。サブドメイン（`www.bit.ly` など）も断る。リンクのページ（`linktr.ee` など）は、行き先が見えるので受け付ける。
- 通報：アプリの、リンクを開く前の確かめの「通報する」から、今の通報の仕組み（機能仕様書 4.2.7）で通報する。対象はそのリンク。理由・回数の上限・運営へのメールは、発信者や予定の通報と同じ。リンクの通報は、メールにリンクの題名と URL を入れる。
- 公開のページには、通報を置かない（今の通報は、アプリのサインインが前提のため）。
- 運営は、通報を確かめ、問題があれば、そのリンクを SQL で消すか、発信者を停止する（機能仕様書 4.6.7）。手順は、環境構成「通報と停止」。
- 自分がオーナーの発信者のリンクには、「通報する」を出さない。

#### 4.6.5 つないだ SNS のリンク

| 項目 | 内容 |
| --- | --- |
> 2026-11-19 に、SNS のアイコンの列で SNS に行けるからと一度やめたが、その列を v1.1.0 では出さないことにした（4.6.7）ので、同じ日に元に戻した。列ができるまでは、つないだ SNS もボタンで出す。決めは下のとおりで、やめる前と同じ。

| 機能概要 | つないだ SNS（本人確認済み）のアカウントのリンクを、リンク集に自動で入れておく。発信者は、そこから並べ替え・題名の変更・削除を始められる |
| 事前条件 | 発信者が、SNS を本人確認済みでつないでいる |
| 関連画面 | リンク集の編集（画面定義書（設定・発信者）2.3.19） |
| 入力項目・バリデーション | なし（サーバーが入れる） |

<kbd>補足・実装メモ</kbd>

- 2026-11-19 本人：「デフォルトで連携しているものは全部追加した状態で作ってあげて、そこから編集開始できるようにしたい」。下の細かい決めも、2026-11-19 に本人が決めた。
- 題名はサービス名（「YouTube」「X」「Instagram」「ツイキャス」「Twitch」）、URL はそのアカウントのプロフィールのページ（アプリの SNS のリンクと同じ。YouTube は `https://www.youtube.com/channel/{チャンネル ID}`）。
- 入れる時：SNS が本人確認済みになった時（アプリでつないだ・発信者の登録で受け渡した・運営が付け替えたなど、どこから確認済みになっても同じ）に、リンク集のいちばん下に足す。データベースのトリガーで行う。
- 入れたあとは、ふつうのリンクと同じ。並べ替え・題名と URL の変更・削除ができ、押された数も数える。ただし、アプリの発信者ページには出さない（4.6.2。公開のページにだけ出る）。
- 一度足したアカウント（発信者・SNS・アカウントの組）は、データベースに記録し、二度と足さない。発信者がそのリンクを消したあとも、同じアカウントをつなぎ直したときも、足さない。
- 同じ SNS で別のアカウントにつなぎ直したときは、新しいアカウントのリンクを足す。前のアカウントのリンクは残す。
- SNS の連携を外しても、リンクは消さない。
- 10件あって足せないときは、足さず、記録もしない（あとで空きができてから、同じアカウントをつなぎ直せば入る）。リンクが足せなくても、SNS の連携は失敗させない。
- 4.6.5 を入れる前からいる発信者：リンク集が空の発信者にだけ、確認済みの SNS のリンクを、アプリの SNS の並び（画面定義書 5.1.7）で一度だけ入れる。リンクがある発信者には足さない。どちらも、今つないでいる SNS は「足した」と記録する。
- 入れる SNS は、本人確認済みのもの全部（この版でアプリに出さない SNS も、確認済みなら入れる）。
- やめていた間（2026-11-19 の数時間。dev だけ）に確認済みになった SNS：元に戻すマイグレーションで、まだ記録の無いものにだけ、いちばん下に足す（トリガーがあった時と同じ）。記録のあるもの（発信者が消したものを含む）は足さない。同じアカウントのページのリンクを発信者が自分で入れていたら、重ねて足さず、記録だけする。

#### 4.6.7 リンクのアイコン

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 公開のページとリンク集の見本で、リンクをすべてボタンで並べ、ボタンの左に行き先のサービスの公式アイコンを自動で付ける |
| 事前条件 | 発信者が、ファンに見せる状態（4.3.1 と同じ） |
| 関連画面 | 共有のページ（ウェブ）、SNSリンク集（画面定義書（設定・発信者）2.3.17）の見本、発信者ページ（画面定義書（ファン向け）2.4.1）のリンクのボタン |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 2026-11-19 本人。Linktree の調べ（docs/concept/linktree-research.md）の C4・C7。決めたことは、すべて出した案のまま（本人「全部おすすめのまま」）。
- SNS のアイコンの列（名前・プロフィール文の下に、本人確認済みの SNS をアイコンだけで並べる）は、v1.1.0 では出さない。次の版で考える（2026-11-19 本人「今は全部ボタンでよい。列は次の版で考える」）。ツイキャスと Twitch を列に入れられない（ツイキャスは色を変えられず余白が大きい、Twitch は第三者のウェブサイトでのロゴを認めない）ので、列とボタンで見え方がちぐはぐになったため。
  - 列のために作ったサーバーの関数 `shared_creator_accounts`（データ設計書 3.3）は消さずに残す。アプリと公開のページは、この版では読まない。
- 並びの決まり（公開のページと見本で1つ。2026-11-19 本人：「リンク集のプレビューはプレビューとして機能してないよ」）：
  - リンクは全部、リンク集に登録した順にボタンで出す。`https://` のものだけ。SNS のアカウントのページを指すリンクも、ふつうのボタンで出す。
  - 押された数（4.6.3）も、全部ボタンの分として数える。
  - アプリ（`CreatorLinkRules.pageLinks`）と公開のページ（公開サイトのリポジトリ（別管理）の Worker の `pageLinks`）に同じ決まりを書き、同じ表（`app/test/fixtures/links_page_cases.json` と、公開サイトのリポジトリ（別管理）の `oiboshi/worker/links_page_cases.json`。中身は同じ）のテストで、ボタンの並びとアイコンが同じ結果になることを確かめる。直すときは両方を直す。
- つないだ SNS のリンクは、列ができるまで、最初から入れておく（4.6.5）。列を入れるときに、列とボタンの両方に出すかを決め直す。
- リンクのアイコン：リンクの URL のドメインから、サービスの公式アイコンをボタンの左に付ける。題名は真ん中のまま。
  - 対象は YouTube（youtube.com・youtu.be）・X（x.com・twitter.com）・Instagram（instagram.com）・Twitch（twitch.tv。アプリの発信者ページだけ。ウェブと見本では付けない）。
  - 見本（アプリ）のボタンのアイコンは、公開のページと同じにする（ウェブで出さないロゴは、見本でも出さない）。アプリの発信者ページのボタン（4.6.2）には、Twitch のロゴを付けてよい（アプリの中は Twitch のブランドの決まりで使えるため。tech-risks.md 2.21）。発信者ページと見本でボタンのアイコンが違ってよい（見本は公開のページの見本なので、公開のページに合わせる。2026-11-19）。
  - Spotify（spotify.com）・Discord（discord.com・discord.gg・discordapp.com）も付ける（2026-11-19 本人が素材の取り込みを承認）。アプリとウェブの両方。
  - ツイキャス（twitcasting.tv）も付ける（2026-11-19 本人「ツイキャスにも付けたい」）。アプリとウェブの両方。素材はアプリの SNS のアイコンと同じ（ツイキャス・ライブのアプリアイコン）。ガイドラインは、ツイキャスを表す目的なら配布のロゴを使ってよいとしていて、ウェブでの使用を禁じていない（tech-risks.md 2.21）。
  - それ以外の行き先は、ふつうのリンクの印（鎖の形）。TikTok（書面の許可が要る）・Amazon（ロゴとスマイルの使用禁止）・BOOTH・pixiv・pixivFANBOX（ロゴで独自のボタンやアイコンを作るのは禁止）などは、各社に確かめるまで、ふつうの印にする。LINE は、決まりの最小の大きさ（スマホで 40px）をボタンのアイコンで満たせないので、ふつうの印にする。
- 素材は、各社の公式の素材から作った画像（`app/assets/brands/`。tech-risks.md 2.21）を、形と色を変えずに使う。公開のページにも同じ画像を置く（公開サイトのリポジトリ（別管理）の `oiboshi/src/assets/brands/`）。ドメインとサービスの対応は、アプリ（`CreatorLinkRules.iconServiceFor`）と公開のページ（Worker）で同じにする。
- 発信者が画像を上げる仕組みは作らない。「Linktree」の名前・ロゴは使わない。「公式」「提携」と読める文言をアイコンの近くに置かない。

#### 4.6.6 追星に誘うリンク

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 追星に誘う公開のページ（`oiboshi.perrii.app/c/{ID}?invite=1`。4.3.6）へのリンクを、リンク集に自動で入れておく。ファンが押すと App Store に進み、入れるとその発信者をフォローした状態で始まる |
| 事前条件 | 発信者のオーナーがいる |
| 関連画面 | リンク集・リンク集の編集（画面定義書（設定・発信者）2.3.17・2.3.19）、共有のページ（ウェブ） |
| 入力項目・バリデーション | なし（サーバーが入れる） |

<kbd>補足・実装メモ</kbd>

- 2026-11-19 本人：「追星のリンクも、この初期のリンク集に入れておいて」。下の細かい決めも、2026-11-19 に本人が決めた（案のまま）。
- 題名は「追星ですべてを受け取る」（2026-11-19 本人。前は「追星で配信の通知を受け取る」。ファンに向けた言い方。名前は長いことがあるので入れない）。前の題名のまま（発信者が変えていない）のリンクは、マイグレーションで新しい題名に書き換えた。発信者が変えた題名は残し、押された数・並び・URL は変えない。URL は `https://oiboshi.perrii.app/c/{発信者 ID}?invite=1`。
- 入れる時：発信者を登録した時（`register_creator`）。オーナーを入れたあと、SNS のリンクより先に入れるので、リンク集の先頭になる。
- 入れたあとは、ふつうのリンクと同じ。並べ替え・題名と URL の変更・削除ができ、押された数も数える（公開のページでは `/c/{ID}/l/{リンク ID}` で数えてから、誘う用のページへ送る）。
- 一度入れたら記録し（データ設計書 3.1.34。`service` は `oiboshi`、`account` は `invite`）、発信者が消したあとも二度と入れない。
- 10件あって入れられないときは、入れず、記録もしない。
- 4.6.6 を入れる前からいる発信者（オーナーのいる発信者。4.6.5 で SNS のリンクが入った発信者も含む）：今の並びを崩さないよう、いちばん下に一度だけ足す。10件あれば足さない。オーナーのいない確認用の発信者には入れない。
- アプリの発信者ページ（4.6.2）には出さない（ファンはもう追星を入れているため）。その発信者の誘う用の URL を指すリンクを隠す。リンク集の着地の画面の見本（公開のページの見た目）と押された数、編集の画面には出す。
- 公開のページでは、リンク集に誘う用のリンクがあるとき、ページの下の追星への入口の「App Store で入れる」とその説明を出さず、「アプリで開く」だけを残す（同じ行き先のボタンを2つ並べないため）。
