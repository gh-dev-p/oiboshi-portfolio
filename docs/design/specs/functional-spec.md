## 2. 用語定義

| 用語 | 定義 |
| --- | --- |
| ユーザー | アプリを使う人。起動時に、匿名でサインインする。全員が、ファンとして推しを追える（2.1） |
| ファン | ある発信者から見て、その発信者のチームメンバーでないユーザー。推しを追う側として使う。ほかの発信者のチームメンバーも、その発信者から見ればファン |
| 発信者 | 配信・投稿・予定を、追星に出す顔。ユーザーとは別のもので、チームが運用する。SNS のアカウントを連携して登録する |
| チーム | 1人の発信者を運用するユーザーの集まり。発信者ごとに1つ |
| チームメンバー | チームに入っているユーザー。ログイン方法が要る。役割は、オーナーと一般メンバー |
| オーナー | チームメンバーの役割。チームに1人。発信者の課金を持つ |
| 一般メンバー | チームメンバーの役割。オーナーでないチームメンバー（未実装） |
| 推し | ファンがフォロー中の発信者 |
| 配信 | ライブ配信。配信中の判定と、本人の配信の映像の再生を扱う |
| 配信中 | いま配信している状態。サーバーが1分ごとに確かめる |
| 埋め込みビューア | ホームの推しレーンの下に置いて、配信を流すもの。ページと一緒にスクロールする（4.3.4）。ホームのものだけを指す（発信者ページには置かない） |
| 固定ビューア | 配信か推しの動画を、画面のいちばん上に据え付けて流し続けるもの。下部ナビのスイッチで出し消しする（4.3.5） |
| ランダム再生 | 固定ビューアで、フォロー中の推しの動画を、推しが続かない順に次々に流すこと（4.3.5.1）。画面では「動画シャッフルモード」と呼ぶ |
| 配信モード | 固定ビューアで、配信中の推しの配信を流している状態。ランダム再生（動画シャッフルモード）と対にして、画面に出す呼び名 |
| 投稿 | 長尺動画・ショート動画・画像・テキストの投稿 |
| 予約 | 配信の、開始予定の時刻。配信サービスから取る |
| イベント | 発信者が手動で登録する、ライブ・トークイベントなどの公演。発信者が手で作る予定は、イベントの公演だけ（2026-11-09 本人） |
| 予定 | 予約とイベントの公演をまとめた呼び名 |
| 実績 | 実際に行われた配信と投稿（日付・SNS・種類・リンク） |
| 新着 | 推しのページを最後に見たあとの投稿 |
| 通報 | ファンが、発信者やイベントの公演の問題を、運営に知らせること |
| 停止 | 運営が、通報などを確かめて、発信者をファンに見せなくした状態 |
| 取得 | サーバー（Edge Functions）が、SNS から更新を取ってデータベースに保存すること |
| 定時実行 | pg_cron が、一定の間隔で Edge Functions を呼ぶ仕組み |
| 確認用の発信者 | 動作の確認のために、運営が SQL で入れた発信者。プランが確認用。公開の前に消す |
| 運営 | 追星を運営する側。アプリの中に役割を持たず、SQL で、確認用の発信者・プラン・優先のフラグ・受付・停止を入れる |
| おすすめ | 推しを探すと推しを選ぶで、言葉が空のときに出す発信者 |
| ログイン方法 | ユーザーに結び付けた、Apple・Google・X・Twitch のアカウント。結び付けたどれでもログインできる |
| 再認証 | 大事な操作の前に、ログイン方法でもう一度ログインして、本人かを確かめること |
| 退会 | ユーザーのデータを消すこと |
| アカウント連携 | 発信者が、SNS のアカウントを OAuth で確かめ、自分のものとして登録すること |
| 確認済み | アカウント連携で、本人のアカウントだと確かめた状態。取得と表示の対象になる |
| 連携の解除 | 確認済みのアカウントを外すこと。内容はすぐに見せなくなり、90日後に消える |
| 登録待ちの連携 | 発信者として登録の手順で確かめた、まだ発信者に付いていないアカウント |
| 表示するコンテンツ | 連携したアカウントごとに、追星に出す内容（配信・動画・ショート・投稿・予約）の選択 |
| タイプ | 発信者が一覧から3つまで選ぶ、配信の傾向（ゲーム・雑談など）。おすすめに使う |
| 優先のフラグ | 運営が付ける、おすすめに出やすくする印 |
| プラン | 発信者の種別と料金の種類。基本プラン・永年無料・運営・確認用 |
| 基本プラン | 一般の発信者のプラン。料金はかからない |
| X連携プラン | 基本プランの発信者が使う、X の連携の有料のサブスク（月290円）。オーナーが加入する |
| 取り戻し | オーナーが退会した発信者を、90日のうちに、SNS の連携で確かめて自分のものに戻すこと |
| 受付 | 発信者の登録と取り戻しを受け付けるかの、アプリ全体の設定 |

### 2.1 ユーザーと発信者の区分け

人（ユーザー）と、追星に出る顔（発信者）を分けて扱う。区分けは、次の3つの軸で決める。

**ユーザー：チームメンバーかどうか**

| 区分 | 条件 | できること |
| --- | --- | --- |
| チームメンバーでないユーザー | 匿名でもよい | ファンとして推しを追う |
| チームメンバー | ログイン方法がある（4.1.4） | ファンとして推しを追う。加えて、自分のチームの発信者を運用する |

- 「ファン」は、人の区分ではなく、発信者から見た立場を指す。ある発信者の決まりで「ファンに見せない」と書いたときは、その発信者のチームメンバーだけに見せることを指す。

**チームメンバーの役割**

| 役割 | 人数 | できること |
| --- | --- | --- |
| オーナー | チームに1人 | 課金（X連携プランの加入・解約）、チームメンバーの招待・外す・役割の変更、オーナーを譲る、発信者を消す。ほかに、一般メンバーができることの全部 |
| 一般メンバー | 何人でも | プロフィールの編集、表示するコンテンツ、イベントの管理、投稿の管理、SNS の連携の追加と解除 |

- MVP では、チームメンバーはオーナー1人だけ（発信者を登録した人、または取り戻した人）。1人のユーザーが入れるチームも1つまで。一般メンバー・招待・オーナーを譲ること・複数のチームに入ることは、未実装。
- オーナーの退会は、止めない（App Store の審査で、アプリから退会できることが求められる）。一般メンバーを実装したら、退会の前にオーナーを譲ることをすすめる。譲らずに退会したときは、一般メンバーがいればオーナーになるよう知らせ（X連携プランは、新しいオーナーが加入し直す）、いなければ、オーナーが退会した発信者（4.6.6.2）として扱う。

**発信者：プランの種類（4.6.6）**

| プラン | 誰のためか | 料金 | 公開の後 |
| --- | --- | --- | --- |
| 基本プラン | 一般の発信者 | 要らない（X連携プランは有料） | 残る |
| 永年無料 | 初期に入ってくれた発信者 | 要らない | 残る |
| 運営 | 追星の運営自身の発信者 | 要らない | 残る |
| 確認用 | 動作の確認（確認用の発信者） | 要らない | 公開の前に消す |

- プランは、運営が SQL で入れる。チームメンバーは変えられない。
- 使える機能は、プランとオーナーの加入から決まり、別の値としては持たない。基本プランは、X のほかの SNS をいつも取得・表示し、X はオーナーの X連携プランの期限のうちだけ取る。永年無料・運営・確認用は、X も含めて、いつも取得・表示する。
- 運営は、アプリの中に役割を持たない。発信者の側で使う言葉（オーナー・一般メンバー・チーム）と、追星の側で使う言葉（運営）は、混ぜない。

## 4. 各機能の詳細仕様

### 4.1 ユーザー

#### 4.1.1 匿名サインイン

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 入力なしで、匿名でサインインする。ファンに、登録や入力は求めない |
| 事前条件 | なし |
| 関連画面 | ウェルカム |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 初回起動では、ウェルカムの「はじめる」（または「発信者の方はこちら」）を押したときにサインインする。2回目以降は、起動時にサインインする。
- ユーザー ID は、サーバーが振る。ファンに見せるのは、お問い合わせ（4.7.3）のときだけ。
- ファンの名前・アバターなどのプロフィールは持たせない。
- ログインの情報は、端末の安全な保存場所（iOS のキーチェーン、Android の Keystore）に保存する。
- 匿名のままアプリを消すと、Android ではフォローが消える。iOS では、キーチェーンにログインの情報が残るので、入れ直すと同じユーザーに戻ることがある。ログイン方法を足せば、別の端末でも引き継げる（4.1.4）。
- 起動時のサーバーへの接続は、10秒で打ち切る。Firebase の初期化に失敗しても、起動は続ける（通知の機能が使えないだけ）。

> ##### 4.1.1.1 処理フロー
>
> 1. 端末に前回のセッションがあれば、そのまま使う（サーバーでユーザーが消えていても使う）。期限切れなら、更新する。
> 2. サーバーが更新を断ったら（リフレッシュトークンが無効・ユーザーが消えている）、そのセッションを捨てる。通信の失敗では捨てず、オフラインのまま起動する。
> 3. セッションがなければ、匿名でサインインする。
>
> <kbd>異常系</kbd>
>
> - 起動時のサーバーへの接続に失敗・10秒を過ぎた　→　起動できなかったことを、エラーの内容とともに出す（端末の言語で出す）
> - サインインに失敗・通信の失敗でセッションを更新できない　→　ウェルカムからは次の画面へ進む。各画面で「読み込めない」の状態を出し、「もう一度試す」でやり直す

#### 4.1.2 利用規約への同意

| 項目 | 内容 |
| --- | --- |
| 機能概要 | ウェルカムの「はじめる」を押すことを、利用規約とプライバシーポリシーへの同意とする |
| 事前条件 | 初回起動 |
| 関連画面 | ウェルカム |
| 入力項目・バリデーション | なし（同意の文を、ボタンの下に添える） |

<kbd>補足・実装メモ</kbd>

- 「はじめる」のあと、推しを選ぶ・通知の説明を経て、通知の説明の画面を閉じたときに、初回起動を済みにする。
- 「発信者の方はこちら」からは、「はじめる」を押さずに、発信者として登録へ進める（初回起動は済まない）。
- 発信者として登録の同意（4.6.1）は、どの入口から来ても、利用規約・プライバシーポリシー・発信者向けの利用規約の3つをまとめて取る。

#### 4.1.3 退会

| 項目 | 内容 |
| --- | --- |
| 機能概要 | ユーザーのデータを、すべて削除する。取り消せない |
| 事前条件 | サインイン済み |
| 関連画面 | 退会、設定 |
| 入力項目・バリデーション | なし（確認は、退会の画面のボタンで行う） |

<kbd>補足・実装メモ</kbd>

- ユーザーごと消すので、ユーザーに付くデータは、すべて消える（データ設計書 3.1.3・3.1.6・3.1.11 など）。通報（4.2.7）だけは消さず、通報した人を空にして残す。
- ストアのサブスクは、退会しても解約されない。X連携プランに加入中なら、退会の画面で、先に解約するよう案内する。加入中かを読み込めないときも、案内する。
- ログイン方法を結び付けたユーザーは、先に再認証する（4.1.4.1）。匿名のユーザーは、退会の画面のボタンだけで行える。
- カバー画像とユーザーは、サーバー（Edge Function `delete-account`）がまとめて消す。カバー画像は SQL から消せないので、Storage API で消し切ってから、ユーザーを消す。
- 退会できたら、端末内の保存もすべて消し、新しい匿名のユーザーでウェルカムからやり直す。画面モードと言語は、すぐに「端末の設定に従う」に戻す。
- Apple を結び付けたユーザーは、Apple 側のひも付けも取り消す（App Store Review Guidelines 5.1.1(v)）。
- 発信者のオーナーが退会すると、発信者は、すぐにファンに見せなくなり、90日後に発信者ごと消える（4.6.6.2）。90日のうちなら、退会や入れ直しのあとでも、同じ SNS のアカウントの連携で取り戻せる（4.6.1.2。ログイン方法のひも付けも消えるので、本人の確かめには SNS の連携を使う）。退会の画面で、このことを伝える。
- 90日より早く消したいときは、お問い合わせで受け付ける（公開ページ `/data-deletion`）。

<kbd>Apple のひも付けの取り消し</kbd>

- 追星は、Apple のリフレッシュトークンを持たない（ID トークンだけを Supabase に渡す。4.1.4）。そこで、退会の前の再認証で受け取った使い捨てのコード（authorization code。5分で切れる）を、サーバー（Edge Function `revoke-apple`）に渡す。サーバーは、Apple でトークンに替えて、すぐに取り消す。トークンは保存しない（`docs/concept/tech-risks.md` 2.14）。
- iPhone では、Apple を結び付けたユーザーの再認証は、Apple だけで行う。5分以内に再認証が済んでいても、もう一度求める（コードが要るため）。
- サーバーは、コードの Apple のアカウント（ID トークンの `sub`）が、そのユーザーに結び付いた Apple と同じときだけ取り消す。
- 取り消しは、ユーザーを消す前に行う。取り消せなかったときは、ユーザー ID と結果をログに残す（トークンもコードも残さない）。
- Android では、Apple を使えない。ほかのログイン方法も結び付けていれば、それで再認証して退会できるが、Apple のひも付けは取り消せない（iPhone で退会するか、退会のあとに iPhone の設定の「Apple でサインイン」から外すよう案内する）。Apple だけを結び付けたユーザーは、Android では退会できず、iPhone で退会してもらう（4.1.4.1）。

> ##### 4.1.3.1 処理フロー
>
> 1. 退会の画面で「退会する」を押す。
> 2. ログイン方法があれば、再認証する（4.1.4.1）。
> 3. Apple のコードを受け取っていれば、Apple のひも付けを取り消す。
> 4. サーバー（`delete-account`）が、ファンのカバー画像を消し切り、ユーザーを消す。
> 5. 端末のセッションと、端末内の保存を消して、ウェルカムに戻る。
>
> <kbd>異常系</kbd>
>
> - Apple のひも付けを取り消せない　→　退会は進める
> - カバー画像やユーザーを消せない　→　失敗を知らせる（もう一度の退会で、続きから消す）
> - ユーザーを消せたあとの、サーバーへのログアウトの通知に失敗　→　退会は済んだものとして進める

#### 4.1.4 ログイン方法

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 「アカウント作成／ログイン」で、Apple・Google・X・Twitch のどれかを選ぶ。初めてのアカウントなら、いまの匿名のユーザーに結び付ける（アカウント作成）。使ったことのあるアカウントなら、そのユーザーに入り、匿名のあいだのフォローを足し合わせる（ログイン）。結び付けたどれでも、同じユーザーとしてログインできる |
| 事前条件 | サインイン済み |
| 関連画面 | 設定、アカウント作成／ログイン、ログイン方法 |
| 入力項目・バリデーション | ログイン方法（足す・外す） |

<kbd>補足・実装メモ</kbd>

- 使う人に、匿名かどうかは考えさせない。入口は、設定の「アカウント作成／ログイン」の1つだけにし、作成かログインかは、アプリとサーバーが決める（2026-11-10 本人）。
- 発信者として登録するには、アカウント（ログイン方法が1つ以上）が要る（匿名のユーザーは、発信者のオーナーになれない。サーバーでも確かめる）。ファンは、匿名のままでよい。
- アカウント作成では、いまのユーザー ID のまま、匿名ではなくなる（Supabase Auth の `linkIdentity`）。フォローは、そのまま残る。
- ログイン方法は、複数結び付けられる（ログイン方法の画面で足す）。最後の1つは外せない。ほかのユーザーに結び付いたログインは、ログイン方法の画面では結び付けられない。
- 別の端末やアプリの入れ直しのあとも、「アカウント作成／ログイン」から、結び付けたどれかを選べば、そのユーザーに入る。
- 設定には、匿名のときは「アカウント作成／ログイン」を、ログイン方法があるときは「ログイン方法」（値：結び付けたサービスの名前）と「ログアウト」を出す。匿名かどうかは、ログイン方法を読めるまでは、端末のセッションのユーザーで決める。
- ログアウトでは、通知の送り先の登録を消し（4.3.3）、端末のセッションを消して、新しい匿名のユーザーで始める。サーバーへのログアウトの通知に失敗しても、ログアウトは済んだものとする（サーバー側のセッションは、期限で切れる）。
- ログインの前にも、通知の送り先の登録を消す。ログインしなかった・できなかったときは、登録し直す。
- ユーザーが切り替わったら、前のユーザーの状態（ログイン方法、再認証など）は残さない。どの経路で切り替わっても（ログインの処理が失敗扱いなのにセッションだけ切り替わったときなど）、サインインと、それに頼る表示（発信者のタブ・ログイン方法・設定など）を読み直す。
- Apple は、App Store の審査（App Store Review Guidelines 4.8）のために置く。iOS だけに出し、iOS の標準のシートで扱う（ID トークンを Supabase に渡す）。この方式は、Supabase の Apple の Secret Key（6か月で切れる）が要らない。Android には出さない（審査のルールは iOS だけにかかる）。ほかの端末で結び付けた Apple は、Android でも一覧に出し、外せる。
- メールアドレスを返さない X のログインは、Supabase の「Allow users without an email」をオンにして使う。
- メールアドレスを確かめていないログインは足さない（Supabase は、同じメールアドレスのログインを、自動で同じユーザーにまとめるため）。
- ツイキャスと Instagram は、Supabase Auth が対応していないので、ログインには使えない（アカウント連携だけ）。
- SNS のアカウント連携（4.6.2）とログイン方法は、別のもの。どちらを外しても、もう一方は残る。
- アプリ運営用ログイン（2026-11-11 本人）：運営が作ったアカウントに、メールアドレスとパスワードで入る。App Store などの審査の人が、Google・X・Twitch のログインで、初めての端末の本人確認のコードに止められずに入れるようにするため。
  - 入口は、「アカウント作成／ログイン」の下に小さく置く。ふつうのユーザーにも見えるが、目立たせない。「運営用」だけだと、発信者のチームの運営と取り違えるので、「アプリ運営用」と呼ぶ。
  - 入れるのは、運営が作ったアカウントだけ。新しい登録と、パスワードを忘れたときの手続きは作らない。アカウントは、運営が、いまのユーザーにメールアドレスとパスワードを足して作る（ほかのログイン方法は、そのまま残る）。
  - メールアドレスでの新しい登録は、サーバーでも断る（Supabase Auth の Before User Created のフック。関数 `hook_reject_email_signups`。データ設計書 3.3）。アプリを通さずに Supabase Auth の登録を呼ばれても、メールアドレスのユーザーは作られない。ほかのログイン（Apple・Google・X・Twitch）と匿名の新しい登録は、止めない。
  - 入ったあとは、使ったことのあるアカウントへのログインと同じ（下の処理フローの 3〜5。足し合わせの券を受け取り、通知の送り先の登録を消してから入り、フォローを足し合わせる）。
  - メールアドレスとパスワードは、ログイン方法の一覧に出さない（足す・外すもしない）。再認証（4.1.4.1）にも使わない。
  - 5回続けて、メールアドレスかパスワードが違ったら、その端末では5分のあいだ入れない（端末に残す。サーバーの回数の制限とは別）。

> ##### 処理フロー（アカウント作成／ログイン）
>
> 1. 選んだサービスを、いまの匿名のユーザーに結び付ける（`linkIdentity`。Apple は ID トークンで `linkIdentityWithIdToken`）。どのユーザーにも結び付いていないアカウントなら、これで済む（アカウント作成）。
> 2. Supabase Auth が `identity_already_exists`（ほかのユーザーに結び付いている）で断ったら、ログインに切り替える。
> 3. 切り替える前に、匿名のユーザーが、フォローの足し合わせの券をサーバーから受け取る（関数 `start_account_merge`。データ設計書 3.3）。通知の送り先の登録を消す（4.3.3）。
> 4. そのアカウントでログインする（`signInWithOAuth`。Apple は `signInWithIdToken`）。ブラウザの SNS の画面を、もう一度通る（SNS のログインがブラウザに残っていれば、許可の画面は出ずに戻ることが多い）。
> 5. ログインしたら、ログイン先のユーザーが、券で、匿名のユーザーのフォローと表示しない発信者と追いたい（機能仕様書（届ける・広める）4.5.1）を移す（関数 `finish_account_merge`）。移せなくても、ログインは済んだものとする。ユーザーが切り替わったので、表示を読み直す。
>
> - 足し合わせでは、ログイン先のユーザーの状態を優先する。同じ発信者のフォローは1つにする（ログイン先のものを残す）。ログイン先が表示しないにした発信者のフォローは移さない。ログイン先がフォローしている発信者は、表示しないに足さない。移すフォローは、通知のオン・オフ、ファンのカバー画像、既読を引き継ぐ。
> - 移したフォローと表示しない発信者と追いたいは、匿名のユーザーから消す（フォロワー数に2回数えないため）。匿名のユーザーそのものと、ほかの持ち物（通報・通知の設定）は、これまでどおりサーバーに残し、移さない。匿名のユーザーは発信者のオーナーになれないので、発信者は持っていない。
> - 券は使い捨てで、30分で切れる。券を知っているのは、匿名のユーザーの端末だけ。移せるのは、券を出した匿名のユーザーのものだけ（ほかの人のフォローは移せない）。
> - ファンのカバー画像のファイルは、匿名のユーザーのフォルダに残る（URL だけを移す）。
>
> <kbd>異常系</kbd>
>
> - SNS の画面で、許可しなかった・閉じた　→　何もしない
> - 券を受け取れない（通信の失敗など）　→　ログインせずに、失敗を知らせる
> - ほかのユーザーに結び付いたログイン（ログイン方法の画面で足すとき）　→　ほかのユーザーで使われていることを知らせる
> - 結び付け・ログイン・外す・ログアウトに失敗　→　失敗を知らせる
> - 外すログイン方法が、サーバーの一覧にない（ほかの端末で外したなど）　→　外すのに失敗したときと同じく知らせ、一覧を読み直す
> - アプリ運営用ログインで、メールアドレスかパスワードが違う　→　違うことを知らせる。5回続いたら、5分のあいだ入れない
> - アプリ運営用ログインで、入れないあいだ（端末の5分、またはサーバーの回数の制限）　→　しばらくしてからやり直すように知らせる

##### 4.1.4.1 再認証

端末を手にした別の人が、アカウントを乗っ取ったり消したりできないように、大事な操作の前に、結び付けたログイン方法のどれかで、もう一度ログインしてもらう。

| 項目 | 内容 |
| --- | --- |
| 対象の操作 | 退会（4.1.3）、ログイン方法の結び付け・外す（4.1.4）、SNS の連携の解除（4.6.2） |
| 対象外の操作 | X連携プランの解約（4.6.6。ストアのサブスクの管理の画面を開くだけで、解約はストアが本人を確かめて行う）、ログイン・ログアウト（ユーザーが切り替わるだけで、データは消えない）、SNS の連携（OAuth で、その SNS のログインが要る） |
| 確かめ方 | 本人の確認（シート）で、いまのユーザーに結び付いたログイン方法を選び、もう一度ログインする。ログインできたユーザーが、いまのユーザーと同じなら済み |
| 有効な時間 | 済んでから5分。その間は、対象の操作を続けて行っても、もう一度は求めない。済んだユーザーと時刻を、アプリの中だけで覚える（アプリを終えると消える）。いまのユーザーが、済んだユーザーと違えば、済んでいないとみなす |

<kbd>補足・実装メモ</kbd>

- 匿名のユーザー（ログイン方法がない人）には、求めない。確かめる手段がなく、匿名のアカウントは、その端末を持つ人のものとして扱う（4.1.1）。発信者として登録の手順で、最初のログイン方法を結び付けるときも、求めない。
- 確かめるのは、アプリのセッションを切り替えずに行う。使い捨ての Supabase Auth のクライアントでもう一度ログインし、ユーザー ID を比べたら、そのセッションは消す（`docs/concept/tech-risks.md` 2.13）。結び付けていないアカウントでログインすると、空の新しいユーザーができて、残る。
- 選べるのは、その端末で使えるログイン方法だけ（Apple は iOS だけ）。
- SNS のブラウザのログインが残っていると、パスワードを聞かれずに済むことがある（Google・X）。アカウントを選ぶ画面が出るように、Google にはアカウントのヒント（結び付けたメールアドレス）を、Twitch には許可の画面を出し直す指定を付ける。
- サーバーでは確かめない（アプリの中の確認だけ。決定事項 5）。

> <kbd>処理フロー</kbd>
>
> 1. 対象の操作を押す。確認のダイアログがある操作は、先にダイアログで確かめる。
> 2. ログイン方法がない、または、5分以内に済んでいれば、そのまま操作する。
> 3. 本人の確認（シート）を出す。ログイン方法を選び、もう一度ログインする。
> 4. いまのユーザーと同じなら、シートを閉じて操作する。
>
> <kbd>異常系</kbd>
>
> - ログイン方法を読み込めない　→　失敗を知らせ、操作しない
> - この端末で使えるログイン方法がない　→　シートで、iPhone で操作するよう案内する
> - SNS の画面で、許可しなかった・閉じた　→　シートに戻る
> - シートを閉じた　→　操作しない
> - 結び付けていないアカウント・ほかのユーザーに結び付いたアカウントでログインした　→　結び付けたアカウントでログインするよう知らせる
> - そのほかの失敗　→　失敗を知らせる

### 4.2 フォロー・推し

#### 4.2.1 フォロー

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者をフォロー・解除する。フォロー中の発信者を「推し」と呼ぶ |
| 事前条件 | サインイン済み |
| 関連画面 | 推しを選ぶ、推しリスト、推しを探す、発信者ページ |
| 入力項目・バリデーション | 発信者（必須）。同じ発信者は、重ねてフォローできない |

<kbd>補足・実装メモ</kbd>

- フォローの一覧は、自分の分だけ読める。
- 推しリストは、配信中の推しを先に並べる。ほかは、フォローした順に並べる。各行に、配信中ならその配信、そうでなければ次の予定を出す。
- 推しリストと発信者ページの次の予定は、これから1年（366日）以内の予定から選ぶ。終日の予定は選ばない。発信者ページの次の予定は、イベントも選ばない（イベントは、発信者ページの「イベント」に出す）。

> ##### 4.2.1.1 処理フロー
>
> 1. 「フォロー」を押すと、フォローを保存し、ボタンを「フォロー中」にする。
> 2. 「フォロー中」を押すと、フォローを削除する。発信者ページでは、「フォロー中」のボタンの代わりにベルのボタンを置き、ベルのシートの「フォローをやめる」で削除する（画面定義書（ファン向け）2.4.1）。
>
> <kbd>異常系</kbd>
>
> - フォロー・解除に失敗　→　失敗を知らせる

#### 4.2.2 推しの検索

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 名前・ID・SNS のアカウントで、発信者を絞り込む |
| 事前条件 | サインイン済み |
| 関連画面 | 推しを選ぶ、推しリスト、推しを探す |
| 入力項目・バリデーション | 検索の言葉（任意） |

<kbd>補足・実装メモ</kbd>

- SNS のアカウントは、確認済みのものだけを対象にする。YouTube は、チャンネル ID（`UC` で始まる）とハンドル（`@` の名前）の両方で探せる。ハンドルは、サーバーがフォロワー数と一緒に1時間ごとに取り直す。
- 次の表記の揺れは、同じ字とみなす：全角と半角（英数字・記号・カタカナ）、ひらがなとカタカナ、英字の大文字と小文字。
- 言葉の先頭の `@` は、無視する（「@minato」で ID「minato」に合う）。
- 挙動は、Instagram の検索に倣う。打つたびに結果を出し、「検索」で確定する操作は置かない（対象が発信者だけなので、打っている間の一覧が、そのまま結果になる）。
- 推しを選ぶ・推しを探すは、サーバー（関数 `search_creators`、データ設計書 3.3）で探す。打ち終わって 250 ミリ秒待ってから問い合わせる。
- 並び順は、合い方の順（完全一致、前方一致、部分一致）。同じ合い方なら名前順。20 人まで出す。
- 言葉が空のときは、「おすすめ」を出す（4.2.2.2）。
- 推しリストは、フォロー中の推しだけを、手元で絞り込む（表記の揺れの扱いは、同じ）。
- 検索とおすすめに出さない発信者：確認済みの SNS のアカウントがない、オーナーが退会した（4.6.6.2）、表示しないにした（4.2.6）、停止中（4.6.7）。オーナーが退会した発信者は、推しリストにも出さない。確認済みのアカウントがない発信者は、フォロー中なら推しリストに残す。
- 発信者に、確認済みの印は付けない。発信者ページに出す SNS は、確認済みのアカウントだけ。

> ##### 4.2.2.1 処理フロー
>
> 1. 言葉を入力する。
> 2. 打ち終わって 250 ミリ秒たったら、サーバーで探す。
> 3. 名前・ID・SNS のアカウントのどれかに、言葉を含む発信者を、合い方の順に、一覧にする。
>
> <kbd>異常系</kbd>
>
> - 結果が0件　→　見つからなかったことと、名前や ID を確かめるよう出す（推しリストでは、フォロー中にいないこと）
> - 読み込めない　→　「読み込めない」の状態を出す。「もう一度試す」で読み直す

##### 4.2.2.2 おすすめ

- 推しを探すと、初回起動の推しを選ぶで、言葉が空のときに出す。サーバー（関数 `recommend_creators`、データ設計書 3.3）で選び、20人まで返す。
- 出すのは、検索に出せる発信者のうち、フォローしていない発信者。
- 選び方は、発信者のタイプ（4.6.4）と、優先のフラグで決める。
  1. フォロー中の推しのタイプを数える（推しの3人がゲームなら、ゲームは3）。
  2. 数えたタイプを1つ以上持つ発信者を、先に出す。並びはランダムで、重みを付ける。重みは、持っているタイプの数の合計（ゲームと雑談を持ち、推しのゲームが3・雑談が1なら、4）。優先のフラグがあれば、重みを3倍にする。
  3. 残りの発信者（推しがいない、推しにタイプがない、タイプが合わない）は、そのあとに出す。優先のフラグの付いた発信者を先に、それぞれの中はランダムに並べる。
- 推しがいない人（初回起動の推しを選ぶを含む）は、3だけになる。
- 優先のフラグは、初期に入ってくれた発信者などに、恩を返すために、運営が SQL で付ける（`creators.featured`）。発信者は、自分では付けられない。ファンには見せない。
- ランダムなので、読むたびに変わる。画面を開いたときに1回読み、開いている間は、同じ一覧のままにする（フォローしても、その行は消さない。検索の言葉を消したときも、同じ一覧に戻る）。

#### 4.2.3 新着

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 推しのページを最後に見たあとの投稿を、新着とする。推しのアイコンの印（ホームの推しレーンと推しリストの「NEW」の印）と、発信者ページの区切りに使う |
| 事前条件 | フォロー中 |
| 関連画面 | ホーム、推しリスト、発信者ページ |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 最後に見た時刻は、推しのページを開いたときに更新する。見ていなければ、フォローした時刻を基準にする。
- 3日より前の投稿は、新着にしない（新着がたまり続けないようにするため）。
- 発信者ページでは、新着と、それより前の投稿の間に、区切りを出す。投稿がすべて新着なら、区切りは出さない。
- 発信者ページを開いたら、ホームと推しリストの「NEW」の印も、サーバーへの書き込みを待たずに既読にする。書き込みに失敗したときは、次の読み直し（1分ごと）で、サーバーの状態に戻る。

#### 4.2.4 ファンのカバー画像

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 推しのページのカバー画像を、自分の写真に変える。自分にだけ見える |
| 事前条件 | フォロー中 |
| 関連画面 | 発信者ページ |
| 入力項目・バリデーション | 画像（JPEG・PNG・WebP、5MB まで。保存先が確かめる） |

<kbd>補足・実装メモ</kbd>

- 選んでいなければ、発信者のカバーを出す。
- カバーは、発信者のカバーも自分の写真も、横3：縦1で出す（はみ出す部分は切る）。切り取りの画面は置かない。
- 自分の写真を選ぶと、カバーに「表」（推しのカバー）と「裏」（自分の写真）ができる。カバーを押すと、表と裏を切り替える。どちらを出しているかは、推しごとに覚える（端末を替えても同じ）。写真を選んだ直後は、裏を出す。
- 「推しが設定したカバーに戻す」で、自分の写真を外す。
- 選んだ画像は、長辺 1600px まで縮め（縦長の写真も大きいまま上げないため）、JPEG にして、推しごとに1つの画像として上書きする。
- 画像は、自分のフォルダにだけ置ける。読むのは、誰でもできる（データ設計書 7.1）。
- フォローを解除したとき、表示しないにしたとき（4.2.6）、「推しが設定したカバーに戻す」を押したときは、自分の写真を消す。退会でも消える（4.1.3）。

> <kbd>異常系</kbd>
>
> - 写真を選べない・上げられない・戻せない　→　失敗を知らせる

#### 4.2.5 フォロワー数

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者の、SNS ごとのフォロワー数と、その合計を出す |
| 事前条件 | なし |
| 関連画面 | 発信者ページ |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- サーバーが、確認済みのアカウントのフォロワー数を取って、保存する。表示するコンテンツのオン・オフには関わらない。
- 取るのは、YouTube（チャンネル登録者数）・Instagram（フォロワー数）・Twitch（フォロワー数）・ツイキャス（サポーター数）。1時間ごと。Instagram は、「投稿」がオンなら、投稿の取得（15分ごと）で一緒に取る。
- ツイキャスは、1日1回（日本時間の朝4時台）だけ取る。呼び出しの上限（60秒で60回）を、配信中の判定と分け合うため。数がない発信者は、時刻に関わらず取る。
- X は、投稿の取得（1分ごと）で、投稿者の情報と一緒に返るフォロワー数を保存する（新しい投稿があった回だけ更新する）。X を取得する発信者（4.6.6）は、X の「投稿」がオフでも取り続ける（このときは、フォロワー数の取得（1時間ごと）で、1日1回、ユーザーの情報を読む。まだ数がなければ、すぐ読む）。取得しない発信者は、X の数を取らず、出さない（合計にも入れない）。この分の課金は、今後の検討事項とする。
- X連携プランが切れたら、サーバーが、ファンに渡す発信者の情報（データ設計書 3.2.1）から、X の数を外す。加入し直せば、すぐまた出す。
- YouTube の登録者数は、YouTube が上から3桁に丸めて返す（例：742,000）。登録者数を隠しているチャンネルは、数を出さない。
- 合計は、SNS ごとの数を足して、そのうちいちばん粗い丸めの桁で切り捨てる（例：YouTube 525,000 と Instagram 62,961 なら、千の位で切り捨てて 587,000）。正確そうに見える端数を出さないため。
- 連携を外した SNS、確認が外れた SNS の数は、1時間ごとの取得で消す。取得に失敗したときは、前回の数を残す。オーナーが退会した発信者（4.6.6.2）と停止中の発信者（4.6.7）は、数を取らず、最後の数を残す。
- 表示は、さらに縮める。日本語では、1万未満をカンマ区切り（「12,345」）、1万以上を「◯.◯万」（小数第1位まで切り捨て。0 なら「◯万」）、100万以上を「◯万」、1億以上を「◯.◯億」（小数第1位まで切り捨て。0 なら「◯億」）で出す。英語では、1000未満をそのまま、1000以上を「588K」の形（四捨五入）で出す。

#### 4.2.6 発信者を表示しない

| 項目 | 内容 |
| --- | --- |
| 機能概要 | ファンが、発信者を見えなくする。設定から元に戻せる |
| 事前条件 | サインイン済み |
| 関連画面 | 発信者ページ、表示しない発信者 |
| 入力項目・バリデーション | なし（確認のダイアログで行う） |

<kbd>補足・実装メモ</kbd>

- 発信者ページのメニューの「この発信者を表示しない」で行う。自分がオーナーの発信者には出さない。
- 表示しないにすると、フォローを外す。推しの検索・おすすめ・ホーム・スケジュール・月のカレンダーに、その発信者を出さない。
- 表示しない発信者は、ユーザーごとに持ち、本人にだけ効く。発信者には知らせない。退会で消える。
- 設定の「表示しない発信者」で一覧し、「表示する」で戻す。戻しても、フォローは戻らない。

> ##### 4.2.6.1 処理フロー
>
> 1. 発信者ページのメニューで「この発信者を表示しない」を押し、確認のダイアログで「表示しない」を押す。
> 2. 先に表示しない発信者に足し、そのあとフォローを外す（フォローを外すときと同じ処理で、ファンのカバー画像も消す）。前の画面に戻る。
>
> <kbd>異常系</kbd>
>
> - 表示しない発信者に足すのに失敗　→　失敗を知らせる。フォローとカバー画像は、そのまま残す（フォローだけが外れた状態にしない）
> - 足したあと、フォローを外すのに失敗　→　そのまま前の画面に戻る（フォローは、表示しない発信者には効かない。「表示する」に戻したとき、フォローが残っていることがある）

#### 4.2.7 通報

| 項目 | 内容 |
| --- | --- |
| 機能概要 | ファンが、発信者・イベントの公演・リンク集のリンクの問題を、運営に通報する（App Store Review Guidelines 1.2） |
| 事前条件 | サインイン済み |
| 関連画面 | 発信者ページ、予定の詳細、詳細のパネル、イベントの詳細、リンクを開く前の確かめ（リンク集）、通報（シート） |
| 入力項目・バリデーション | 理由（必須。なりすまし・不適切な内容・危険なリンク・その他）、詳しい内容（任意。500文字まで） |

<kbd>補足・実装メモ</kbd>

- 発信者は、発信者ページのメニューで通報する。自分がオーナーの発信者には出さない。
- イベントの公演は、予定の詳細・詳細のパネル・イベントの詳細で通報する。自分がオーナーの発信者の公演には出さない。取得した配信の予約と、投稿には出さない（SNS の内容なので、それぞれの SNS で通報してもらう）。
- リンク集のリンク（届ける・広める仕様書 4.6.4）は、リンクを開く前の確かめのダイアログで通報する。自分がオーナーの発信者のリンクには出さない（v1.1.0 で足す。未実装）。
- 通報は、データベースに入れる（データ設計書 3.1.23）。アプリからは足すだけで、読めない・変えられない。
- 同じ人が、同じ対象を通報できるのは、24時間に1回まで。
- 通報が入ると、サーバーが運営のメール（`support.oiboshi@perrii.app`）に知らせる。件名に「[追星] 通報」を付ける。件名は、送れる長さ（200字）に収まるように、予定のタイトル・リンクの題名・発信者の名前を、見た目の1文字（書記素）で切り、切ったら「…」を付ける。本文には、切らずに全部を入れる。送り方は、環境構成「通報と停止」を参照する。メールを送れなくても、通報は受け付ける（運営は SQL でも確かめられる）。
- 運営は、通報を確かめ、問題があれば、発信者を停止する（4.6.7）か、その予定・リンクを消す。結果は、通報した人に知らせない。
- 利用規約と発信者向けの利用規約に、禁止事項と、通報への対応（確かめて、表示を止めたり消したりすること）を書く。

> ##### 4.2.7.1 処理フロー
>
> 1. 入口の「通報する」「この予定を通報する」を押す。
> 2. 通報のシートで、理由を選ぶ。詳しい内容は任意で書く。
> 3. 「送信」を押すと、シートを閉じて、通報したことを知らせる。
>
> <kbd>異常系</kbd>
>
> - 理由が未選択　→　「送信」を押せない
> - 24時間以内に、同じ対象を通報済み　→　受け付け済みであることを知らせる。シートは閉じない
> - 送れない（対象が見つからないを含む）　→　失敗を知らせる。シートは閉じない

### 4.3 配信

#### 4.3.1 配信中の判定

| 項目 | 内容 |
| --- | --- |
| 機能概要 | サーバーが、全発信者について、各配信サービスに配信中かを問い合わせ、結果を保存する。ツイキャス・Twitch・YouTube に対応する |
| 事前条件 | 発信者が、対象のサービスの確認済みのアカウントを持つ。表示するコンテンツで、「配信」がオン |
| 関連画面 | ホーム、推しリスト、発信者ページ |
| 入力項目・バリデーション | なし（定時実行） |

<kbd>補足・実装メモ</kbd>

- 既定で1分ごとに確かめる。費用が、ファンの人数ではなく、発信者の人数に比例するようにするため。間隔は、SNS ごとに変えられる（4.8.1.2）。
- 配信が始まってから画面に出るまでは、最大で約2分（確認の1分と、アプリの読み直しの1分）。
- 同じ発信者が複数のサービスで同時に配信していたら、ツイキャス → Twitch → YouTube の順で、1つだけ出す。
- 確認した時刻から3分を超えていれば、アプリは配信中とみなさない。
- YouTube は、RSS の新しい順の5本を、Data API で確かめる。無料のクォータに収まる発信者数の上限は、今後の検討事項とする。
- ツイキャスの合言葉付き・メンバーシップ限定・プレミア配信と、Twitch の種類が「live」でない配信は、配信していないものとして扱う。
- 配信を見つけたら、配信の実績（4.5.4）にも記録する。YouTube は、RSS の5本のうちの終わった配信も、実績に書く。
- 保存する項目は、データ設計書 3.1.14 を参照する。

> ##### 4.3.1.1 処理フロー
>
> 1. 定時実行が、配信の確認を呼ぶ（4.8.1）。
> 2. 対象から外れた発信者（未確認になった・「配信」をオフにした・停止した・オーナーが退会した）の配信中の行を消し、終わっていない配信の実績を終える。
> 3. 各サービスに問い合わせ、配信中の行を保存し、配信中でなくなった行を消す。
> 4. 新しく見つかった配信があれば、配信開始の通知（4.3.3）を送る。
>
> <kbd>異常系</kbd>
>
> - 1つのサービスへの問い合わせに失敗　→　ほかのサービスは続ける。その発信者の行は、ほかのサービスで配信が見つかれば上書きし、見つからなければそのまま残す
> - 通知を送れない　→　送り直さない。配信の確認は続ける（4.3.3）

#### 4.3.2 配信の再生

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 配信中の映像を、ホームの埋め込みビューア（4.3.4）と固定ビューア（4.3.5）で、アプリ内で再生する |
| 事前条件 | 発信者が配信中 |
| 関連画面 | ホーム、固定ビューア、発信者ページ（「固定ビューアで見る」） |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 流すのは、発信者本人の配信だけ。他人の配信は流さない。
- ツイキャスは、HLS を直接再生する。YouTube・Twitch は、公式プレイヤーを埋め込む。
- 音を出して自動再生する（最初からミュートにはしない）。受動的に流し続けるため、自動再生が止められても、流れるようにやり直す（Twitch が、音ありの再生を通さずに自分でミュートにしたときは、ユーザーがまだプレイヤーに触っていなければ、1回だけ読み込み直す）。ユーザーが自分で切り替えたミュートは、こちらで外さない。
- ミュートは、YouTube・Twitch は公式プレイヤーの音量の操作で、ツイキャスは映像の右下のボタンで切り替える。
- 配信を流すのは、ホームの埋め込みビューア（4.3.4）と固定ビューア（4.3.5）だけ。発信者ページの中では流さない（2026-11-19 本人）。配信中の発信者のページでは、アイコンを「LIVE」の印にし、「固定ビューアで見る」のボタンで、その配信を固定ビューアで流す（画面定義書（ファン向け）2.4.1）。
- 公式プレイヤーの準備が20秒でできない・読み込みに失敗した・YouTube がエラーを返したときは、再生できないとみなす。
- アプリが前面に戻ったときは、再生し直す。

<kbd>音の扱い</kbd>

- 音を出すのは、いちばん前の映像だけにする。
- 固定ビューアでの再生を優先する（2026-11-19 本人）。固定ビューアを出している間は、投稿ビューアを固定ビューアの下の領域に出し、投稿の動画は自動で流さない。ファンが再生のマークを押したら流し、流している間は固定ビューアを一時停止する。止める・別の投稿に移る・ビューアを閉じると、固定ビューアを流し直す（4.3.5）。前は、投稿の動画の間は固定ビューアの音を消し、YouTube 同士のときだけ固定ビューアの YouTube を止めていた。
- ホームの埋め込みビューアは、投稿ビューアで動画を再生している間、止めずに音を消す。止めると、ビューアを閉じたときに読み込み直しの待ちが出るため。全画面のビューアに隠れている間も流すことは、YouTube の規約（見えていないプレイヤーで流さない）ではグレーだが、一時的に見せていないだけとして、すぐ戻れることを取る。
- 投稿の動画を止める・別の投稿に移る・ビューアを閉じると、埋め込みビューアの配信の音を元に戻す（YouTube の動画・ショートも、公式プレイヤーで一時停止・終わりにしたら、流していないものとして扱う。2026-11-19）。もとからミュートだったら、ミュートのまま。
- iOS では、YouTube の動画が音を出すと、後ろの配信が止まることがある。音を戻すときに、止まっていれば流し直す（YouTube の配信は、いちばん新しい位置まで進めてから流す）。Twitch は、音を消している間も、止められたら音なしで流し直す（ホームの埋め込みビューア。固定ビューアは、投稿の動画を流している間は一時停止するので当たらない）。
- 前で別の動画が音を出している間に作った埋め込みビューアのプレイヤーは、音を消して始め、前の動画が終わったら音を出す。

> <kbd>異常系</kbd>
>
> - 再生できない　→　ホームの埋め込みビューアと固定ビューアでは、エラーの印だけを出す（「もう一度試す」は出さない）

#### 4.3.3 配信開始の通知

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 推しが配信を始めたとき、プッシュ通知で知らせる |
| 事前条件 | 通知の許可、全体のスイッチがオン、その推しの通知がオン |
| 関連画面 | 通知の説明、通知設定、発信者ページ |
| 入力項目・バリデーション | 全体のスイッチ、推しごとのオン・オフ |

<kbd>補足・実装メモ</kbd>

- FCM で送る。
- 通知の許可は、初回起動のとき、推しを選んだあとに、理由を説明する画面を出してから、OS の許可の画面を出す。「いまはしない」も選べる。初回起動で OS の許可の画面を出すのは、この1回だけ。
- 一度も許可を求めていないときは、通知設定から OS の許可の画面を出せる。一度断ったあとだけ、端末の設定アプリへ案内する（iOS は、許可を求めたことのないアプリを、設定アプリの通知の一覧に出さないため）。Android は、OS が「まだ求めていない」と「断った」を分けないので、OS の許可の画面を出したことを端末内に残して分ける。

<kbd>送る決まり</kbd>

- 送るとき：配信中の判定（4.3.1）で、発信者の配信が新しく見つかったとき。1つの配信（サービスの配信 ID）につき1回だけ送り、あとで見つけ直しても送り直さない。送ったかの印は、配信の実績（4.5.4）に付ける。実績がもう終わっていれば、送らない。
- 同じ発信者が複数のサービスで同時に配信したときは、出す1つ（4.3.1）だけを見る。その配信が終わったあと、もう1つの配信が開始から30分以内なら、新しい配信として扱う。
- 同じ発信者の通知は、30分に1回までにする（実際に送った通知の時刻から数える）。30分以内に見つけた別の配信は、送らず、前の通知で知らせた扱いにする。
- 送らないとき：見つけた時点で、配信の開始から30分より経っている配信（見張りを始める前から続いていた配信など）。オーナーが退会した発信者（4.6.6.2）と、停止中の発信者（4.6.7）の配信。
- 通知の鍵（サービスアカウント）がサーバーにない・形が違うときは、送らず、送ったことにもしない（鍵を直したあと、開始から30分以内の配信なら送る）。
- 送る相手：その発信者をフォローしていて、その推しの通知（`follows.notify`。予定の事前通知と同じスイッチ）と、全体のスイッチ（`user_settings.notifications_enabled`。行がなければオン）の両方がオンのユーザーの、登録したすべての端末。
- 中身：タイトルは「{発信者の名前}が配信を始めました」、本文は配信のタイトル（空なら「{サービス名}で配信中」）。同じ発信者の通知は、新しいものに置き換える。30分のうちに届かなかった通知は、捨てる。Android には、優先度を高くして送る。
- 文言は、送り先の端末の表示言語（日本語・英語）で作る（i18n設計書 6.5）。
- Android では、チャンネル「配信開始の通知」で出す。利用者は、端末の設定で、このチャンネルだけを切り替えられる。

<kbd>受け取ったとき</kbd>

- 通知を押したとき　→　アプリを開き、推しのタブで、その発信者のページを開く。固定ビューアで流しているものは変えない。初回起動が済んでいなければ、済んでから開く。
- アプリを開いているときに届いたとき　→　OS の通知は出さず、スナックバーで知らせ、「開く」で、押したときと同じ画面を開く。

<kbd>端末の登録</kbd>

- 端末ごとに、FCM の送り先と、通知の言語（アプリの表示言語）をサーバーに登録する（データ設計書 3.1.22）。登録は、OS の通知が許可されていて、初回起動が済んでいるときに行う。
- 登録するとき：起動、ユーザーが変わったとき、通知を許可したとき、FCM が送り先を変えたとき、言語を変えたときなど。
- 1つの端末は、最後に登録したユーザーだけに結び付く。ほかのユーザーが登録していた送り先は、いまのユーザーに移す。
- ログアウト・ほかのユーザーへのログインでは、切り替える前に、いまのユーザーから、その端末の登録を消す。消せなくても、切り替えは進める（切り替えたあとの登録で、新しいユーザーに移る）。退会では、ユーザーと一緒に消える。
- 送るときに、FCM が「もう届かない」（`UNREGISTERED`）か「送り先の誤り」（`INVALID_ARGUMENT`）と返した送り先は、消す。ただし、2台以上に送って、すべてが `INVALID_ARGUMENT` なら、通知の中身の誤りとみなして、消さない。

> <kbd>異常系</kbd>
>
> - 送れない　→　記録だけを残し、送り直さない

#### 4.3.4 ホームの埋め込みビューア

| 項目 | 内容 |
| --- | --- |
| 機能概要 | フォロー中の推しが配信中なら、ホームの推しレーンの下に、配信の映像を流す（埋め込みビューア）。複数の推しが配信中なら、帯を横に払うか、帯の矢印で切り替える |
| 事前条件 | フォロー中の推しが配信中 |
| 関連画面 | ホーム |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 推しレーンの下（全体タイムラインのいちばん上）に置き、ホームの中だけで流す。帯の構成は、画面定義書 2.2.1 を参照する。
- 帯の「LIVE」と配信元の印を押すと、配信ページを外部で開く（YouTube・Twitch の規約：配信元を示し、配信元へ辿れるようにする。ツイキャスにも、そろえて出す。tech-risks.md 2.22・2.23）。推しのアイコンを押すと、その推しの発信者ページを開く。
- 配信中の推しを1人ずつ、推しレーンと同じ順に並べる。帯を横に払うか、矢印を押すと、前後の推しに移る。端の推しの次は、反対の端の推しに戻る（周回する）。映像の上では払えない（YouTube の規約：プレイヤーへのタッチで、アプリの操作を起こさない。どのサービスでも同じ操作にそろえる）。
- 流すのは、いま出している1人の配信だけ。ほかの推しは、サムネイルを出す。
- 音を出して自動で流す（4.3.2）。映像を押すと、プレイヤーを操作できる。発信者ページには移らない。
- 映像は、画面の幅いっぱいの 16:9 にする（YouTube の規約の最小の大きさ 200×200 を満たす）。映像の上には、ツイキャスの音の印のほか、何も重ねない。
- 流すのは、埋め込みビューアの半分以上が画面に見えている間だけ。ホームのタブを出していないとき、ホームのタブの中で別の画面を開いているときは、サムネイルを出す（YouTube の規約：見えるまで自動で流さない。自動で流すプレイヤーは、1画面に1つまで）。投稿ビューアを開いている間は、流したまま音を消す（4.3.2）。
- 固定ビューアが出ている間は、埋め込みビューアを出さない（映像が上と下に2つ並ばないように）。固定ビューアを切ると、固定ビューアで流していた推し（帯で切り替えたなら、切り替えた先の推し）を出す。
- Twitch の配信も、ほかと同じく流す。画面の幅いっぱいなら、埋め込みの最小の大きさ（400×300）に反しないと判断した（decisions.md）。Twitch の返事で認められなければ、やめる。
- 配信の情報は、ホームの読み直し（1分ごと）で新しくする。
- 推しレーンで、配信中の推しのアイコンを押すと、埋め込みビューアをその推しに切り替える（固定ビューアで流していれば、固定ビューアのまま切り替える）。埋め込みビューアで流している推しを押すと、その推しの発信者ページを開く。
- 全体タイムラインには、配信中の YouTube の配信枠（RSS に動画として入るもの）を出さない。終わったあとのアーカイブは、動画として出す。

#### 4.3.5 固定ビューア

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 配信か、フォロー中の推しの動画を、画面のいちばん上に据え付けて流し続ける。受け身で、ユーザーの操作を止めずに流す（ながら見）。ユーザーは、流したまま、好きな画面で好きなことをする。下部ナビのスイッチで、いつでも出し消しする |
| 事前条件 | なし |
| 関連画面 | 下部ナビを出す画面、ホーム、発信者ページ、投稿ビューア |
| 入力項目・バリデーション | 下部ナビのコントローラー（固定ビューアのスイッチ。押すとオン・オフ、はじくか、触れて出るヒントから選ぶと、再生・停止、動画シャッフル、配信、次、前。動画シャッフルでは、右・左に引っ張ったまま止めると早送り・巻き戻し） |

<kbd>補足・実装メモ</kbd>

- スイッチを入れると、流すものを選んで流す。切ると、閉じる。
- 下部ナビのスイッチは「コントローラー」で、はじく向きで固定ビューアを操作する（2026-11-17 本人。決定事項 参照。前の「左右に引っ張って配信とランダム再生を入れ替える」は、これに置き換えた）。
  - 向き：上＝再生・停止、上右＝動画シャッフル（4.3.5.1）、上左＝配信、右＝次、左＝前。下は使わない。次・前は、今流しているものに合わせる（ランダム再生なら前後の動画、配信なら前後の配信中の推し。帯の払い・矢印と同じ並び）。
  - 決め方：押した所からの指の動きが 36pt に届いたら、真上からの角度で決める。上は ±22.5°、上右・上左は 22.5〜67.5°、右・左は 67.5〜135°、それより下は使わない。届かなければ何もしない（押したことにもしない）。
  - はじいている間は、アイコンが指について動き（46pt まで）、操作が決まる所まで来ると振動する。離すと元に戻る。
  - ヒント（2026-11-18 本人。前は長押しで出していた）：指が触れたらすぐ、触れている間だけ、アイコンの周りに5つの向きのヒント（下部ナビの丸と同じすりガラスの小さい丸に、帯と同じアイコン。上は流しているなら停止、止めているか切っているなら再生。上右の動画シャッフルは重なった動画、上左の配信は電波の印）を出し、下部ナビのほかのメニュー（左端の丸と楕円）を隠す。指を動かしたら、アイコンは指について動き、ヒントは出したまま、離した向きの操作をする。決まる所まで滑らせると、その向きのヒントを主色にして振動する。動かさずに離したら、出し消しを切り替える（押したのと同じ）。
  - 再生・停止：止めている間は、プレイヤーを外して止める（動画は再生位置を控え、流し直すと続きから）。「停止しました」「再生を再開しました」と知らせる。流すもの（配信の推し・動画）が変わるか、スイッチを切ると、止めていたのをやめる。
  - 動画シャッフル・配信：モードが切り替わったときの知らせ（下の「配信モードとランダム再生が切り替わったら」）を出す。もうそのモードなら、止めていれば流し直す（「再生を再開しました」）。配信中の推しがいなければ、今流しているものを流し続け、「配信中の推しはいません」と知らせる。流せる動画がなければ、帯のボタンと同じく「流せる動画がありません」と知らせる。
  - 次・前：帯の矢印と同じく切り替え、「次の動画」「前の動画」「次の配信」「前の配信」と知らせる。切り替えられなければ（配信中の推しが1人など）、何もしない。
  - 早送り・巻き戻し（2026-11-19 本人）：動画シャッフル（ランダム再生）で YouTube の動画を流しているときだけ、右・左に引っ張ったまま止めると、早送り（右）・巻き戻し（左）にする。さっと払うと、今までどおり次・前。
    - 見分け方：右・左の向きが決まって（36pt）から 0.4 秒のあいだ、右・左のまま指を離さなければ、引っ張ったまま止めたとみなす（払う指は、向きが決まってからふつう 0.2 秒ほどで離れる）。そのとき1回振動する。それより早く離せば、次・前。
    - 速さ：最初は1秒に5秒分。同じ向きのまま引っ張り続けると、1秒ごとに 10・20・40・60 秒分と速くなり、最大で1秒に60秒分。向きを変える（右から左へ）と、最初の速さに戻る。右・左から外れて（真ん中・上など）いる間は、動かさない。
    - 動かしている間は、数字や位置の帯は出さない。固定ビューアの動画そのものが進む・戻るのを見てもらう。プレイヤーには、間引いて位置を送る（YouTube の IFrame API の `seekTo`）。前に送ってから 0.4 秒たち、前の位置へ動き終えて（プレイヤーの位置が送った位置から2秒以内に入って）から次を送る。動き終えなくても 1.5 秒たてば送る（tech-risks.md 2.38）。
    - 離したら、そこから再生する（止まっていても流す）。次・前にはしない。動画の頭と、終わりの3秒手前で止まる（終わりまで動かすと、引っ張っている間に次の動画に移るため。終わりの近くに動かして YouTube が「終わった」と知らせても、引っ張っている間は次に進まず、位置を戻す）。離したあと最後まで流れたら、今までどおり次の動画に進む。
    - 配信（Twitch・ツイキャス・YouTube のライブなど）、コントローラーで止めているとき、投稿ビューアで動画を流しているとき、動画がまだ流れ始めていないとき（長さが分からない）、再生できないと分かった動画では、早送り・巻き戻しにせず、引っ張ったまま止めても今までどおり離したときに次・前にする。
  - スイッチを切っているとき：入れてからその操作をする。上は、入れて流す（止めない）。動画シャッフルは、ランダム再生で流し始め、「動画シャッフルモードに切り替えました」と知らせる。配信は、配信中の推しがいればその配信を流して「配信モードに切り替えました」、いなければ入れて（ランダム再生で流し）「配信中の推しはいません」と知らせる。次・前は、入れて流し始めてから、前後に切り替える。
- 帯のボタンと払いは、コントローラーとは別に残す。
- 推しの誰かが配信中のあいだは、コントローラーを開いたとき（触れてヒントが出たとき）の、上左の「配信」のアイコンの右上に、小さな赤い点（ライブの色）を出す。下部ナビのコントローラーのアイコン（開く前の丸）にも、左上（配信のアイコンが出る向き）に同じ点を出す（2026-11-19 本人「コントローラアイコンにも、左右斜め上（各アイコンがある方向）に配信中／NEW バッジつけて！」）。いなければ出さない。配信中かどうかは、ホームの「LIVE」と同じ情報（ホームの読み直し、1分ごと）で決める。発信者のナビにもファンのナビにも出す（2026-11-18 本人）。
- 推しに新しい動画があるあいだは、コントローラーを開いたときの、上右の「動画シャッフル」のアイコンの右上に、配信の点と同じ形・大きさ・位置で、ホームの「NEW」の色の点を出す（2026-11-19 本人）。コントローラーのアイコンにも、右上（動画シャッフルのアイコンが出る向き）に同じ点を出す（配信の点と両方あれば、両方出す。2026-11-19 本人）。新しい動画は、動画シャッフルに入る動画（YouTube の動画。生配信の枠と、隠した投稿（4.4.4）を除く）のうち、ホームの「NEW」と同じ決め方（最後にその推しを見てから、3日以内に投稿された）で新しいもの。見るのは、ホームの全体タイムラインに読んだ投稿。その推しを見ると消える（「NEW」と同じ）。発信者のナビにもファンのナビにも出す。
- スイッチの初めの状態（2026-11-10 本人。初めて開いたときに、空のホームの見た目を固定ビューアで邪魔しない）：
  - 推しが0人（初めて開いたときなど）：入れない（切った状態）。
  - 推しが1人以上：入れる（起動したときから流す）。
  - 推しを0人から1人以上にしたとき：推しを追加した画面では何もしない。次にホームを開いたときに入れる。
  - 推しをまた0人に戻したとき：切る（0人のときの形に戻る）。
  - ユーザーがスイッチで切ったとき：切ったことを端末内に覚え、アプリを開き直しても、推しを足しても、切ったままにする。0人のために自動で切ったときは、覚えない（推しができたら入れる）。
  - ユーザーがスイッチで入れたとき（固定ビューアのボタンなどで流し始めたときも）：切ったことの記録を消す。推しが0人でも入れたままにし、推しを探すへの案内を出す。
- 流すものの選び方：配信中の推しがいれば、その配信（ホームの埋め込みビューアで出していた推しを先に、ほかは推しレーンの順）。いなければ、推しの動画のランダム再生（4.3.5.1）。どちらもなければ、推しを探すへの案内を出す。案内を出している間に推しが配信を始めても、切り替えない（スイッチを入れ直すと、選び直す）。
- 続きから流す（2026-11-18 本人）：固定ビューアで最後に流していたものを端末内に覚え（アプリを入れ直したら消えてよい）、次に固定ビューアを開いたとき（スイッチを入れたとき・起動して入れたとき）、上の選び方より先に使う。
  - 推しの YouTube の動画：その動画を、覚えた位置から流す。ランダム再生の1本目として流し、終わったら、ランダム再生を続ける。配信中の推しがいても、動画を先にする。位置は、流している間5秒ごと、アプリが裏に回るとき、閉じたとき・止めたとき（投稿ビューアで動画が流れ始めて止めたときを含む）に覚え直す。その動画が、いまのランダム再生で流せる動画になければ（隠した・推しでなくなった・配信中の配信枠など）、ふだんの選び方にする。
  - 配信：続きの位置はない。最後に流していた推しがまだ配信中なら、その配信を流す。終わっていれば、ふだんの選び方にする。
  - ほかの動画（Instagram・X の動画、推しでない人の動画など）を流したら、覚えていたものを忘れる（ふだんの選び方に戻す）。
  - 位置の取り方と、位置から始める方法は、YouTube の IFrame API の `getCurrentTime`（1秒ごとに控える）と、プレイヤーの `start`（秒）を使う。YouTube の生配信（配信中の動画）は、位置から始めると再生できないので、位置を覚えない（`getVideoData().isLive` のときは位置を分からないとし、いちばん新しい位置から流す）。
- 固定ビューアのボタン（ホームの埋め込みビューア・投稿ビューア）、発信者ページの「固定ビューアで見る」か、投稿ビューアの左へのスワイプで流し始めたら、スイッチも入れる。
- 発信者ページの「固定ビューアで見る」（2026-11-19 本人）：その発信者が配信中で、固定ビューアでいまその配信を流していないとき（スイッチを切っている・別の配信や動画を流している・コントローラーで止めている）に出す。押すと、その配信を流す（止めていたなら、流し直す）。流している間は出さない。発信者ページを開くだけでは、流しているものを変えない。
- 流すのは1つだけ。あとから流したもの（配信か投稿の動画）に切り替える。
- 画面のいちばん上に据え付け、タブを移っても残す。アプリの画面は、固定ビューアの下から始め、重ねない。大きさと帯の構成は、画面定義書 2.4.3 を参照する。
- 映像の上には何も重ねない（YouTube の規約）。閉じるボタンは置かない（スイッチで消す）。
- 帯を横に払うか、矢印を押すと、配信は前後の配信中の推し（推しレーンと同じ順。周回する）に、ランダム再生は前後の動画に切り替える。映像の上では払えない（YouTube の規約）。
- 配信と YouTube の動画は、プレイヤーをそのまま操作できる（YouTube の規約：プレイヤーの機能を塞がない）。Instagram・X の動画は操作できず、押すと投稿ビューアで開く。
- 帯の推しのアイコンを押すと、その推しの発信者ページを開く。固定ビューアは、そのまま流す。
- 投稿の動画の帯の配信元のアイコンを押すと、投稿ビューアで、その投稿を見ていた位置から開く。閉じると、固定ビューアは、ビューアで見ていた位置から続ける。
- 配信を流している間は、発信者ページを閉じたあとも、その発信者の配信中かを1分ごとに確かめる。終わったと分かったら、知らせて、次に流すものを選ぶ。終わったばかりの配信は、3分のあいだ選ばない（推しの情報の読み直しが1分ごとで、終わった配信をまだ配信中とみなすことがあるため）。
- 配信モードとランダム再生（動画シャッフルモード）が切り替わったら、何を流しているか分かるように知らせる（スイッチを入れて流し始めたとき・同じモードの中の切り替え・投稿ビューアから入れた投稿の動画では知らせない）。
- 配信からランダム再生に戻したら（帯のボタン・コントローラーの上右のどちらでも）、配信に切り替える前のランダム再生の続きから流す（2026-11-19 本人「動画シャッフルモードは配信モードに切り替えても、再生位置などを保持しておいてほしい」）。新しくシャッフルし直さない。
  - 続けるもの：流していた動画、切り替える直前の再生位置、シャッフルの順番（帯の矢印・払いの次・前でたどる並び）、止めていたか（コントローラーで止めた、または YouTube のプレイヤーで一時停止した。止めていたら、止めたまま戻し、コントローラーの「再生」で流す）。
  - 覚える先はアプリの中だけ（端末には書かない）。配信の間に、ほかの配信に切り替えても、スイッチを切って入れ直しても残る（入れ直して配信がなく、ランダム再生になったときも続きから流す）。アプリを開き直したときは、上の「続きから流す」に従う（配信に切り替えたので、最後に流していたのは配信になる）。
  - その動画が、いま流せなければ（隠した・推しでなくなった）、忘れて、新しくシャッフルする。新しくランダム再生を始めたときと、続きから流したときにも忘れる。
- 投稿ビューアから入れた投稿の動画（YouTube）が最後まで流れたら、ランダム再生に移る（配信に切り替える前のランダム再生があれば、その続きから）。
- ランダム再生の帯から開いた投稿ビューアで、固定ビューアのボタンを押す（左へ払う）と、ランダム再生を続ける。見ていた投稿を見ていた位置から流し、終わったらランダム再生の次の動画に進む。
- 投稿ビューアを開いている間（2026-11-19 本人。前は、投稿ビューアが画面全体を覆い、YouTube を止めていた。tech-risks.md 2.35）：
  - 投稿ビューアは、固定ビューアの下の領域（固定ビューアを隠さない所）に出す。固定ビューアを出していなければ、画面全体に出す。固定ビューアの出し消し・大きさの変化にも合わせる。
  - 固定ビューアは、隠れず何も重ならないので、流し続け、そのまま操作できる。固定ビューアでの再生を優先し、投稿の動画（YouTube・動画ファイル・カルーセルの中の動画）は自動で流さず、サムネイルに再生のマークを出す（固定ビューアで流すボタンは今までどおり）。ファンが押したら流す（2026-11-19 本人「固定ビューアでの再生を最優先にしよう。固定ビューアが開いていれば、投稿ビューアでは動画を自動再生しない」。押したら「流して、固定ビューアは止める」と本人が答えた）。
  - 投稿の動画を流している間は、サービスを問わず、固定ビューア（配信・動画）を一時停止する（プレイヤーを外す）。投稿の動画を止める・別の投稿に移る・投稿ビューアを閉じると、配信はいちばん新しい位置から、動画は止めた位置から流し直す。投稿の動画は、別の投稿に移って戻ったら、また押すまで待ち、押したら止めた位置から流す。これで、1つの画面に自動で流れる YouTube のプレイヤーが2つ並ぶこともない（YouTube の規約、Required Minimum Functionality）。固定ビューアを出していなければ、投稿の動画は今までどおり自動で流す。
  - 帯の配信元のアイコンで、流している動画そのものをビューアで開いたときは、同じ動画を2つ流さないよう、固定ビューアを止める（今までどおり）。
  - 投稿ビューアの YouTube のプレイヤーは、規約の最小の大きさ（200×200）より小さくしない。縦長の動画で幅が足りなければ、プレイヤーを 200 まで広げる（左右はプレイヤーが黒で埋める）。狭い領域で 200×200 が取れなければ（固定ビューアで縦長の動画を流しているとき、小さい画面など）、流さずにサムネイルだけを出す（2026-11-19 本人。固定ビューアの大きさは変えない）。
  - 投稿ビューアがかぶさっている間は、タブの中にモードの切り替えなどの知らせを出さない（隠れて見えないため）。
  - プレイヤーを外すときは、WebView に空のページを読み込んで、確実に止める（外しても WebView はすぐには消えず、Twitch は裏で流れ続けたため）。
- 流している投稿を、発信者が隠したら（4.4.4）、次に流すものを選ぶ。
- アプリの中だけに出す。アプリの外（OS のピクチャ・イン・ピクチャ）には出さない。

> ##### 4.3.5.1 推しの動画のランダム再生
>
> 1. フォロー中の推しの YouTube の動画（ショートを除く）を、新しい順に600本まで読む。隠した動画（4.4.4）、生配信（配信中・配信予定）の枠、これから公開する動画は流さない。
>    - 生配信かは、サービス（YouTube・Twitch など）ではなく、中身で決める（2026-11-18 本人）。YouTube の配信枠は RSS に動画として入るので、サーバーが `videos.list` の `liveBroadcastContent`（`live`・`upcoming`）で投稿に印を付け（データ設計書 3.1.12 `live_status`）、アプリは印のある投稿を流さない。発信者に出す配信は1つだけ（ツイキャス → Twitch → YouTube の順）なので、出さなかった YouTube の配信にも印を付ける。
>    - 生配信が終わってアーカイブ（録画）になったものは、動画として流す。
>    - 配信は「配信」（コントローラーの上左・帯のボタン）で流し、動画シャッフルには入れない。
> 2. 1周で、推しを1人1本ずつ、シャッフルした順に流す（推しごとに同じくらい流し、多く投稿する推しに偏らない）。推しが2人以上なら、同じ推しを続けない（周のつなぎ目でも続けない）。
> 3. 推しの動画は、その推しの中でシャッフルし、全部流したら、シャッフルし直して繰り返す。シャッフルし直したとき、その推しの直前の動画を、すぐには流さない。
> 4. 動画が最後まで流れたら、次の動画に進む。前に戻ったぶんは、流した順にたどる。
>
> <kbd>異常系</kbd>
>
> - 動画を再生できない（削除・非公開・埋め込みの禁止など）　→　2秒見せてから、次の動画に進む。続けて5回再生できなければ、先へ進むのをやめる（通信が切れているときに、読み込み続けない）
> - ランダム再生に切り替えたが、流せる動画がない・読めない　→　流しているものはそのままにして、知らせる

### 4.4 投稿

#### 4.4.1 投稿の取得

| 項目 | 内容 |
| --- | --- |
| 機能概要 | サーバーが、YouTube・Instagram・X の投稿を取得し、保存する |
| 事前条件 | 発信者が、対象の SNS の確認済みのアカウントを持つ。表示するコンテンツで、「動画・ショート」（YouTube）・「投稿」（Instagram・X）がオン。X は、X連携プランに加入しているか、プランが永年無料・運営・確認用（4.6.6） |
| 関連画面 | ホーム、発信者ページ |
| 入力項目・バリデーション | なし（定時実行） |

<kbd>補足・実装メモ</kbd>

- 取得の間隔は、YouTube と X が1分ごと、Instagram が既定で15分ごと（4.8.1.2）。方式は、platforms.md 5章を参照する。
- 取得に、本人の連携は要らない。公開のアカウントを指定するだけで取れる。本人のアカウントかの確認（なりすまし対策）は、4.6.2 を参照する。
- Instagram は、運営のトークン1つで Business Discovery を呼び、プロアカウントの公開されている投稿とフォロワー数を取る。運営のトークンには期限があり、自動では延びないので、運営が切れる前に手で作り直す（`docs/dev/environment.md` 5.2）。発信者が連携した本人のトークンで取る形（Meta のアプリの審査を通した形）は、v1.0.0 のあとに回す。
- v1.0.0 のアプリは、Instagram の投稿・フォロワー数・アカウントを読まない（4.6.2。次の版で出す）。サーバーは、確認済みのアカウントの取得を続ける。
- YouTube と X は、新着だけを足す。最初の1回だけ、さかのぼって取る（1回の実行で、SNS ごとに5人まで）。
  - YouTube：さかのぼりは、Data API で、新しい順に100件。新着は、RSS（直近15件）で取る。RSS は、チャンネルのアップロード一覧（再生リスト。チャンネル ID の先頭 `UC` を `UU` に替えたもの）のものを使う。チャンネルの RSS は、新しい動画が載るまでに数分〜数時間かかることがあるが、アップロード一覧のものは上げた直後から載る（2026-11-09。中身は同じ）。配信中の判定と配信の予約（4.3・4.5.1）も、同じ RSS を見る。
  - X：さかのぼりは、過去90日の投稿を、300件まで。期間内が3件より少なければ、期間より古くても、最新の3件を取る。新着は、前回の最新の投稿（隠した投稿を含む。4.4.4）より新しいものだけを取る。
- Instagram は、直近の投稿（100件）を毎回取り直して置き換える（画像の URL が数日で切れるため）。呼び出しの上限は、今後の検討事項とする。
- X は、本人の投稿だけを取る。リポストとリプライは取らない。取れた件数に課金される。
- X は、投稿と一緒に返る投稿者の情報（`expansions=author_id`）から、X でのプロフィール画像・表示名・@ユーザー名を保存する（X の投稿の投稿者の行に出す。4.4.3）。呼び出しは増やさず、費用は変わらない。新着がない回は返らないので、前に保存した値のままにする。
- X の本文の t.co のリンクは、元の URL に置き換える（画像・動画を指すものは消す）。画像・動画は、全部を持つ（最大4つ）。動画（GIF を含む）は、720p 前後の mp4 を1本持ち、投稿ビューアで再生する。
- YouTube は、ショートを、リンクの形と長さで見分ける。配信の予約枠と配信のアーカイブも、RSS に載るので、動画として入る。コミュニティ投稿は、公式の取得手段がないので、取らない。
- カルーセル（Instagram のカルーセルと、画像・動画が2つ以上ある X の投稿）は、全部の画像と動画を持ち、投稿ビューアで横に送って見る。タイムラインのカードは、1枚目を出す。
- アプリで再生できない動画（Instagram が動画を返さないリール、X の動画本体が取れない投稿、YouTube の公式プレイヤーが再生できない動画など）は、SNS を問わず、再生できないことを出し、押すと元の SNS で開く。

> ##### 4.4.1.1 処理フロー
>
> 1. 定時実行が、取得を呼ぶ（4.8.1）。
> 2. 各 SNS から新着を取り、保存する（あれば更新する）。
> 3. 保存範囲の枠（4.4.2）から外れた投稿を削除する。新着がない回も、削除する。
>
> <kbd>異常系</kbd>
>
> - 1人の取得に失敗　→　その人を飛ばし、ほかの発信者は続ける
> - Instagram の運営のトークンが無効・期限切れ（エラーの 190）　→　Instagram は全員の取得に失敗する（ほかの SNS は続ける）。前に取った投稿は残るが、画像と動画の URL が数日で切れて出なくなる。運営がトークンを作り直す（`docs/dev/environment.md` 5.2）
> - YouTube のさかのぼりに失敗　→　その回の RSS の新着は保存する。1日あけてから、さかのぼりをやり直す（失敗し続けるアカウントで、毎分 YouTube のクォータを使わないため）。さかのぼりは、失敗したことのないアカウントを先にする

#### 4.4.2 投稿の保存範囲

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 取得した投稿を、SNS ごとに、期間と件数の枠で残す |
| 事前条件 | なし |
| 関連画面 | なし |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- SNS ごとに、新しい順に上限の件数までのうち、過去90日以内のものを残す。上限は、YouTube 100件、Instagram 100件、X 300件。期間より古くても、最新の3件は残す。
- 枠で消すのは、取得のとき。新着がない回も消すので、投稿しない人の投稿も、90日を過ぎたら消える。
- 表示するコンテンツをオフにした・X連携プランが切れたなど、取得の対象から外れた投稿は、枠では消さない。ファンには出さない（4.6.3）。
- オーナーが退会した発信者（4.6.6.2）、停止中の発信者（4.6.7）、連携を解除したアカウント（4.6.2）は、取得を止める。投稿は出さず、90日を過ぎたら消す。
- 本人が SNS で消した投稿は、次のとおり反映する。
  - YouTube：1日1回、保存している動画の全部がまだあるかを Data API で確かめ、返らなかった動画（消した・非公開にした）を消す（4.8.1）。確かめるのに失敗したときは、何も消さない。
  - Instagram：取り直しで、なくなった投稿を消す（4.4.1）。
  - X：投稿から35分後の読み直し（下の編集の反映）で、そのときまでに消えていた投稿は消す。それより後に消したものは、自動では追わない。消えたかを確かめると、残っている投稿の読み取りに課金されるため。発信者が、追星で手で隠す（4.4.4）。
- 本人が X で編集した投稿は、次のとおり反映する。X は、投稿から30分まで、5回まで編集でき、編集するたびに新しい ID になる。
  - 取得のとき、前の版の ID を持つ投稿が返ったら、前の版を新しい版に置き換える。前の版を隠していたら（4.4.4）、新しい版も隠した投稿として扱う。
  - 投稿から35分たった投稿を、1回だけ X から読み直し、新しい版があれば置き換える。いいね数などの数も、このとき新しくなる。読み直しは、投稿1件につき読み取り1回（新しい版があれば、もう1回）ぶん課金される。

#### 4.4.3 投稿の表示

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 投稿を、タイムラインに日時順に混ぜて出す。押すと、全画面のビューアで1件ずつ見る |
| 事前条件 | サインイン済み |
| 関連画面 | ホーム、発信者ページ、投稿ビューア、詳細のパネル |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- ホームは、フォロー中の推しの投稿を、最新の50件を1分ごとに読み直す。下までスクロールすると、50件ずつ続きを読み、過去90日まで出す。
- 読み直しでは、続きで読んだ投稿を残したまま、最新の50件を入れ替える。前に読んだ投稿とつながらない（50件を超えて増えた）とき、または推しを足したときは、続きを捨てて、最新の50件から出し直す。
- 発信者ページは、残してある投稿をすべて出す。
- 投稿の見た目は、SNS を問わず同じ枠にそろえ、SNS はプラットフォームのアイコンで見分ける（画面定義書 2.2.1）。X の投稿も同じ枠（推しのアイコン・名前、本文、画像）で出し、X の表示の決まりで外せないものを足す。右上に、左から X での表示名・@ユーザー名の2段、プロフィール画像（どれも X のプロフィールに結ぶ。4.4.1 で保存したもの）と X のロゴを、灰色の小さい字（左そろえ）と、2段の文字と同じ高さの画像・ロゴで出し（2段の文字の欄は、画像の幅の2倍の 44 まで）、推しの名前の下の投稿からの時間と「Xで見る」を X の投稿に結ぶ。いいね数・返信数は出さない。追星の発信者の名前・アイコンは X に合わせて変えない（同期しない）。
- ビューアは、上下のスワイプで前後の投稿に移り、右へのスワイプで閉じる。左へのスワイプか固定ビューアのボタンで、再生できる動画を、見ていた位置から固定ビューアで流す（4.3.5）。カルーセルは、左右のスワイプで画像を送る。「開く」で、元の SNS を外部で開く。画像と動画ファイルは、2本の指かダブルタップで拡大でき（上限 4 倍）、拡大している間は、投稿・画像を送らない（YouTube の埋め込みは拡大しない。画面定義書 2.5.1）。
- ビューアでは、YouTube の動画・ショートを公式プレイヤーで再生する。
- 本文とプロフィール文の URL は、リンクにして、押すと外部で開く。`https://` のない URL（`youtu.be/…`・`example.com/…` の形）も、リンクにする。途中で `…` で切れた形で保存された URL は、押すと元の投稿を外部で開く。

> ##### 4.4.3.1 処理フロー（ビューアの移動順）
>
> 1. ホームから開いたとき：全体のタイムラインの順。
> 2. 発信者ページから開いたとき：その推しの投稿を、新しい順。
> 3. タイムスケジュール（詳細のパネル）から開いたとき：その推しの、その日の投稿（絞り込みのあと）を、新しい順。

#### 4.4.4 投稿を隠す（発信者）

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者が、自分の投稿を、追星で隠す（ファンに出さなくする）。隠した投稿は、また出せる。元の SNS の投稿は消えない |
| 事前条件 | その発信者のオーナー |
| 関連画面 | 投稿の管理（画面定義書（設定・発信者向け）2.3.8） |
| 入力項目・バリデーション | なし（取り消せるので、確認のダイアログは出さない） |

<kbd>補足・実装メモ</kbd>

- 発信者メニューの「投稿の管理」で、自分の投稿を一覧して、行ごとのトグル（オン＝出す、オフ＝隠す）で切り替える。投稿ビューアには、隠すメニューを置かない（ファンと同じ見た目にし、投稿の管理を1か所にまとめるため）。
- 2026-11-19 に、「追星から削除」（取り消せない）を「隠す」（また出せる）に置き換えた（本人）。元の SNS の投稿が消えないことは、投稿の管理の画面に一文で書く。
- 隠した投稿は、すぐにファンに見せなくする。ホーム・発信者ページ・スケジュール（月のカレンダーの点を含む）・投稿ビューア・固定ビューアの動画シャッフルのどこにも出さず、投稿が見られた数（届ける・広める仕様書 4.2.3）にも数えない。サーバーが、ファンには読ませない（データ設計書 3.1.12・6.2）。
- 隠した投稿も、投稿の本体は残す（保存の枠から外れたら、ほかの投稿と同じく消える）。次の取得で同じ投稿が返っても、隠したままにする（データ設計書 3.1.13）。
- 隠したら・また出したら、タイムライン・発信者ページ・スケジュールを読み直す。隠した投稿の動画を固定ビューアで流していたら、次に流すものを選ぶ（4.3.5）。
- 2026-11-19 より前に「追星から削除」した投稿は、隠した投稿として扱う。本体はもう消えているので、次の取得で同じ投稿が返ったときに、隠した投稿として戻り、投稿の管理に出る（Instagram と YouTube の直近の投稿）。X は前回より新しい投稿だけを取るので、戻らない。
- 公開中の v1.0.0 のアプリの「追星から削除」は、隠すと同じ動きにする（データ設計書 3.3 の `remove_post`）。v1.0.0 の投稿の管理には、隠した投稿は出ない。

> <kbd>異常系</kbd>
>
> - 隠せない・また出せない　→　失敗を知らせる

### 4.5 予定・カレンダー

#### 4.5.1 配信の予約の取得

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 配信の、開始予定の時刻を、配信サービスから取り、保存する |
| 事前条件 | 発信者が、対象のサービスの確認済みのアカウントを持つ。表示するコンテンツで、「予約」がオン |
| 関連画面 | タイムスケジュール、月のカレンダー、予定の詳細 |
| 入力項目・バリデーション | なし（定時実行） |

<kbd>補足・実装メモ</kbd>

- 取るのは、ツイキャス・Twitch・YouTube。Instagram と X は、取れない。X・Instagram の配信の予定や告知は、追星には載せない（2026-11-09 本人）。取り方と検証の結果は、platforms.md 6章を参照する。
- サーバーが30分ごと（既定。4.8.1.2）に、今から31日先までの予約を取る。
- 取った予約は、予定（イベントの公演と同じ表。データ設計書 3.1.16）に保存する。取り直して、なくなった予約（取り消し、始まった配信）は消す。まだ始まっていない予約は、開始予定から12時間まで残す。
- YouTube は、RSS の直近15本から、予約を探す。予約を作ったあとに、15本より多くの動画が出ると、その予約は見つからなくなり、消える。
- 取得の対象から外れたアカウント（未確認になった、連携を解除した、「予約」をオフにした、オーナーが退会した、停止中になった）の予約は、次の取得で消す。
- 取った予約は、発信者のオーナーも、アプリから編集・削除できない（取り直すと戻るため）。
- 終了時刻は、取れないか、空のことが多い（取れるのは Twitch と、YouTube の一部）。終了時刻のない予定は、配信なら1時間で描く（4.5.3）。
- タイトルが空の予約は、「配信」と出す（Twitch はカテゴリ名があれば、それを使う）。Twitch の取り消した回と、休みの期間の回は、取らない。
- 1つの取得元が失敗しても、他は続ける。失敗した取得元の予約は、前回のまま残す。
- 取った予約と、イベントの公演が、同じ配信を指すときは、両方を出す（決定事項 5）。

#### 4.5.2 イベント

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者が、イベント（ライブ・ツアーの1公演・トークイベントなど）を登録する。発信者が手で作る予定は、イベントの公演だけ（2026-11-09 本人） |
| 事前条件 | 発信者として登録済み（4.6.1） |
| 関連画面 | イベントの管理、イベントの登録（編集を兼ねる）、タイムスケジュール、月のカレンダー、予定の詳細、イベントの詳細 |
| 入力項目・バリデーション | タイトル（必須、1〜200文字。見た目の1文字で数える。前後の空白は除く）、公演の日付（必須。今日の365日前から730日後まで選べる。編集では、入っている日付が範囲の外でも選べるように広げる）、時刻未定、開始時刻（時刻未定でなければ必須）、終了時刻（任意）、会場（任意）、チケットリンク（任意。何本でも。`https://` で始まる URL だけ）、リンクごとに広告か |

<kbd>補足・実装メモ</kbd>

- 発信者メニューの「イベントの管理」で、自分のイベントの公演を一覧し、登録・編集・削除する。予定の詳細と詳細のパネルでは、イベントの公演で、オーナーのときだけ「編集」を出す（イベントの編集を開く）。
- プラットフォーム（YouTube・X・Instagram・ツイキャス・Twitch）を選んで自由に作る予定（前の「カレンダー予定」）は、なくした。X・Instagram の配信の予定や告知は、追星には載せない。前に登録した、そうした予定は、消した（2026-11-09 本人。データ設計書 3.1.16）。
- 取得した配信の予約（4.5.1）は、イベントの管理に出さず、編集も削除もできない。
- 1つのイベントは、1つの公演（決定事項 1）。本体（タイトル）・チケットサイトのリンク（何本でも。PR はリンクごと）・公演（日時・会場・公演のページの URL）からなる（データ設計書 3.1.16〜3.1.18）。ツアーの名前は、公演ごとのイベントのタイトルに入れる。保存は、関数 `save_event` で、リンクと公演ごとまとめて行う。画面で「チケット」と呼ぶのは、イベントのリンク。
- イベントの公演は、プラットフォームを持たず、汎用のアイコンで出す。リンクが広告なら、「PR」と出す。
- イベントの管理の行を押すと、イベントの登録の画面を編集で開く（タイトルとチケットリンクも一緒に直せるように）。
- リンクの形とタイトルの長さは、データベースでも確かめる（データ設計書 3.1.16）。タイトルは、入力欄と保存の確かめを、同じ数え方（見た目の1文字）にする。
- 終了時刻を決めないと、その日の終わり（24:00）まで表示する（2026-11-19 本人。登録の画面の終了の欄の下に、そのことを書く）。終了時刻が開始時刻より前か同じなら、翌日の時刻とみなす。
- 同じ発信者の中で、同じチケットのページ（形をそろえた URL が同じ）を指すリンクは、1本だけ持てる。公演の候補では、チケットの URL が変わっても二重に登録しないよう、同じ日で、同じとみなせる会場で、開演が食い違わない公演も、登録済みとみなす。
- 開演の時刻が分からない公演は、「時刻未定」で登録する（予定の行は終日にする）。イベントの公演で終日のものは、どの画面でも「時刻未定」と出す。公演のページの URL があれば、発信者がページを開いて時刻を読める。

<kbd>チケットサイトで探す</kbd>

- アーティスト名（初期値は発信者の名前）でチケットサイトを検索し、ヒットしたアーティストを並べる。選ぶと、そのアーティストの公演を1日1行で並べる（画面定義書（設定・発信者向け）2.3.12・2.3.13）。今日より前の公演は、出さない。
- 探すのは、チケットぴあ・イープラス・ローチケ・楽天チケット。ZAIKO・LivePocket・TIGET は、アーティストという単位がなく、関係ないイベントが多く混ざるので除く。楽天チケットは、アーティストの代わりに、名前を含むイベントの1行を出す。
- 同じ公演を複数のサイトが売っていれば1行にまとめ、登録するとサイトごとのチケットリンクを持つ。公演の候補から登録すると、1公演を1つのイベントとして作る。
- サイトのページは、発信者が「探す」・アーティストを押したときだけ開く（受付が終わった公演も漏らさず並べるため、イベントのページまで開く）。定期的な検索はしない。
- イベントの候補からは、発信者がページを確かめて登録する。公演が複数あれば、発信者が1つ選ぶ。読み取れない項目は、登録の画面で足してもらう。

<kbd>URL からの読み取り</kbd>

- チケットの URL を貼って「読み取る」を押すと、発信者がアプリの中でそのページを自分で開く。「このページから読み取る」で、表示しているページから読み取りに要る部分（構造化データ・OGP・日付や「開演」を含む行）だけを、Edge Function `read-event-url` に送る。関数は、タイトルと公演（日付・開始・終了・会場）の下書きを返す。開始の時刻が読めなければ、発信者が入れるまで保存できない。
- サーバーは、外のページを読みに行かない。ページを見ているのは発信者自身なので、ボットによる取得に当たらないようにするため。
- `read-event-url` は、`https://` の URL と、1,000,000 文字までの中身だけを受け付ける。IP アドレス・ポートの指定・内向きの名前（`localhost`・`.local` など）の URL は、受け付けない。発信者のオーナーだけが呼べる。

> ##### 4.5.2.1 処理フロー（登録）
>
> 1. 必須の項目を入力して、「保存」を押す。
> 2. イベントを保存して、前の画面に戻る。保存・削除のあとは、イベントの管理・スケジュール・発信者ページの予定を読み直す。
>
> <kbd>異常系</kbd>
>
> - 必須の項目が未入力・タイトルが長すぎる・リンクが `https://` で始まる URL でない　→　保存せず、どこが違うかを出す
> - 同じチケットのページを指すリンクが、ほかのイベントにある　→　登録済みであることを知らせる
> - 保存に失敗　→　失敗を知らせる

> ##### 4.5.2.2 処理フロー（編集・削除）
>
> 1. イベントの管理で行を押すか、イベントの詳細・予定の詳細で「編集」を押す。
> 2. 登録と同じ画面を、入力済みで開く。直して「保存」を押すと、イベントを書き換えて、前の画面に戻る。
> 3. 消すときは、「このイベントを消す」を押し、確認のダイアログで消す。イベントを消すと、公演とチケットリンクも消える。
>
> <kbd>異常系</kbd>
>
> - 保存・削除に失敗　→　失敗を知らせる

#### 4.5.3 予定の表示

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 予定を、タイムスケジュール（推し全員、1日）と、月のカレンダー（1人または全員）で見る |
| 事前条件 | サインイン済み |
| 関連画面 | タイムスケジュール、月のカレンダー、予定の詳細、詳細のパネル、発信者ページ |
| 入力項目・バリデーション | 日付、拡大・縮小 |

<kbd>補足・実装メモ</kbd>

- 予定の見分けは、プラットフォームの色とアイコンで行う。推しごとの色は使わない。
- 配信とイベントの公演は、時間の長さを持つブロックで出す。終了時刻のないものは、イベントの公演はその日の終わり（24:00）まで、配信は1時間で描き、終端をフェードさせる（2026-11-19 本人。前は、発信者が決めるデフォルトの長さ（4.6.5。廃止）で描いていた）。
- 投稿は、時刻を出さない小さなチップで、投稿した時刻の位置に出す。前の投稿から30分以内の投稿は、「+N」にまとめる（続けて近接すれば、同じ「+N」に入れる）。
- タイムスケジュール（1週ぶん）と月のカレンダー（1か月ぶん）は、推し全員の投稿を、600件まで読む。
- 重なったときの並べ方と、表の見た目は、画面定義書（スケジュール）を参照する。
- 表の要素（配信・予定・投稿）を押すと、種類を問わず、表の下の詳細のパネルに中身を出す。
- 月のカレンダーは、予定に加えて、実績（4.5.4）を、日ごとに出す。
- 発信者ページには、次の予定、イベント、カレンダーへのボタンを置く。推しリストの各行には、次の予定の日時を出す（4.2.1）。
- ホームの「次の予定」は、今日のこれからの予定（イベントと終日の予定を除く）を、ホームと発信者ページの「イベント」は、これからのイベントを、それぞれ2件まで出す。3件以上あれば「ほか N 件」を出し、「イベント」ではイベント一覧を開く。
- イベント一覧は、これからのイベント（1年以内。開催中を含む）を、月ごとに区切って日付順に並べる。1人のイベント（発信者ページから）と、推し全員のイベント（ホームから）の両方に使う。
- イベントの詳細には、日時・会場と、リンクごとの購入のボタンを出す。チケットの販売の状況は出さない。
- イベントのリンク（チケットリンク・公演のページ）を開く前に、行き先のドメインを出して確かめる（どこから開くときも同じ）。`https://` で始まらないリンクは開かない。

#### 4.5.4 実績

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 実際に行われた配信と投稿を、予約の有無にかかわらず、実際の時刻で、カレンダーとタイムスケジュールに反映する |
| 事前条件 | なし |
| 関連画面 | タイムスケジュール、月のカレンダー |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

- 実績は、日付・SNS・種類・リンクを、連携した日から消さずに残す。投稿の本体（画像・本文）は、4.4.2の枠で消す。
- 配信の実績：
  - 配信中の判定（4.3.1）で配信を見つけたら、記録を作る。配信が終わったら、最後に配信中と確かめた時刻を、終了の時刻にする。
  - その回に確かめられなかったサービス（取得に失敗した・取得の間隔で確かめない回）の配信の記録は、終えない（ほかのサービスで配信が見つかっても）。次に確かめられた回に決める。
  - YouTube は、配信中の判定で見る RSS の5本のうち、終わった配信の、実際の開始と終了の時刻も記録する（見張る前の配信・プレミア公開も入る）。
  - ツイキャスと Twitch は、1時間ごとに、「配信」がオンのアカウントの、直近の終わった配信を20件まで取って、まだ記録のない配信を足す（Twitch は、アーカイブを残している配信だけ）。ツイキャスの合言葉・メンバーシップ限定・プレミア配信は、足さない。
  - Twitch の実績のリンクは、チャンネルのページにする（アーカイブは消えることがあるため）。
- YouTube の配信の実績は、YouTube API の規約（取ったデータを30日を超えて持つなら、取り直すか消す）に合わせて、最後に取ってから25日を過ぎたものを、1日1回（4.8.1）取り直す。まだある動画は書き直し、もうない動画（消された・非公開）は実績を消す。1日に取り直すのは2,500件まで。
- 配信の実績は、タイムスケジュールでは、実際の開始から終了までのブロックで（終わった予定と同じく、薄く）、月のカレンダーでは、配信の行で出す。
- 配信中の配信は、実績ではなく、配信中の配信（4.3.1）として出す。
- 取得した予約（4.5.1）の開始予定の30分前から12時間後までに、同じ発信者・サービスの実績が始まっていたら、その予約を出さない（その配信の予約とみなす。予約は次の取得で消えるが、それまで二重に出さないため）。
- 投稿の実績は、残してある投稿（4.4.2の枠）だけを出す。枠から外れた投稿の実績は、今後の検討事項とする。
- 連携を解除したときは、その SNS の実績を、すぐに出さなくする。90日持ち、過ぎたら消す。90日のうちに同じアカウントを連携し直したら、また出す（4.6.2）。
- オーナーが退会したときは、発信者ごと出さなくし、90日後に発信者ごと消す（4.6.6.2）。

#### 4.5.5 スケジュールの絞り込み

| 項目 | 内容 |
| --- | --- |
| 機能概要 | タイムスケジュールと、みんなのカレンダー（月のカレンダー）に出す推し、プラットフォーム、内容を選ぶ |
| 事前条件 | サインイン済み |
| 関連画面 | 絞り込み（シート）、タイムスケジュール、月のカレンダー |
| 入力項目・バリデーション | 推し（複数。1人以上）、プラットフォーム（複数。SNS と「イベント」。1つ以上）、内容（配信・投稿。スイッチ）。配信・投稿・予定のない推しを隠す（オン・オフ）は、シートではなくヘッダーのアイコンで切り替える |

<kbd>補足・実装メモ</kbd>

- シートの選択は、表示のボタンを押したときに反映する。「リセット」は、シートの中の選択を、すべて表示に戻す。
- 「イベント」は、プラットフォームのない予定（イベントの公演）を出すかを決める。イベントの公演の出し入れは、この「イベント」だけでする（2026-11-09 本人）。初期値は全部。
- 推しを1人も、またはプラットフォームを1つも選んでいないときは、表示のボタンを押せない。
- 配信中の配信（予約のないものも含む）は、「配信」のスイッチとプラットフォームの選択で出し入れする。
- 推しの絞り込みは、外した推しを覚える。あとからフォローした推しは、外していないので出す。フォローを外して、出す推しが1人もいなくなったときは、全員を出す。
- タイムスケジュールとみんなのカレンダーは、絞り込みを別々に持つ。どちらも、アプリを起動しているあいだ保つ。

### 4.6 発信者向け

- 発信者メニュー（画面定義書 2.2.2）の一番上のプロフィールカードで（2026-11-19 本人。もとは「自分のページ」の行）、自分がオーナーの発信者のページ（ファンが見るのと同じもの。画面定義書 2.4.1）を開く。オーナー向けの別のページは作らない。

#### 4.6.1 発信者の登録

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者として登録する。2つの手順と、規約への同意（利用規約・プライバシーポリシー・発信者向けの利用規約）が済むと、登録できる |
| 事前条件 | サインイン済み |
| 関連画面 | 発信者として登録、アカウント連携、プロフィールの編集 |
| 入力項目・バリデーション | 手順（SNSアカウントを連携、プロフィールを入力）、規約への同意 |

<kbd>補足・実装メモ</kbd>

- 手順1（SNSのアカウントを連携）は、アカウント連携（4.6.2）と同じ OAuth で確かめる。登録の前は発信者がないので、確かめたアカウントは、ユーザーごとの「登録待ちの連携」（データ設計書 3.1.6）に持ち、登録するときに発信者のアカウントに移す。
- 手順2（プロフィールを入力）で、名前・プロフィール文・アイコンに加えて、ID を決める（英小文字・数字・`_`・`-` の1〜40文字。あとから変えられない）。タイプ（4.6.4）とカバーも選べる（任意）。
- 登録は、サーバー（Edge Function `register-creator`、関数 `register_creator`）で、1回で行う。発信者・オーナーを作り、登録待ちの連携を発信者のアカウントに移す。そのあと、アイコン・カバー・タイプを保存する。それに失敗しても、登録は済んでいる（プロフィールの編集で直してもらう）。
- 登録に、プランの加入は要らない（基本プランは無料。4.6.6）。登録すると、基本プランになる。X のアカウントは、加入の前でも連携できる。X の取得と表示は、X連携プランに加入すると使える。
- 登録できるのは、アカウント（ログイン方法。4.1.4）があるユーザーだけ。登録の流れの中では、ログイン方法を結び付けない。設定の「発信者として登録する」は、アカウント作成の前は押せない。ウェルカムの「発信者の方はこちら」は、匿名なら、先にアカウント作成／ログイン（シート）を出し、済んだら登録へ進む（2026-11-10 本人）。
- 受付は、運営が SQL で開け閉めする（`app_settings` の `creator_registration_open`）。
- サーバーが断るのは、匿名のユーザー・受付が閉じている・すでにオーナー・登録待ちの連携がない・ID が使われている・登録待ちの連携がほかの発信者で確認済み、のとき（結果は、データ設計書 3.3 の `register_creator`）。
- 登録すると、手順1で確かめたアカウントが確認済みになる。確認済みの SNS のアカウントがない発信者（運営が SQL で入れた発信者や、連携を全部解除した発信者）は、検索・おすすめに出さない（4.2.2。なりすまし対策。2026-11-09）。
- 発信者に、確認済みの印は付けない（4.2.2）。ファンに出る発信者は、全員が確認済みのため（2026-11-09）。
- 登録した人には、下部ナビに発信者のタブを出し、発信者メニューに入れる。
- 登録の画面は、設定のほか、ウェルカムの「発信者の方はこちら」からも開ける（4.1.2）。
- 運営が SQL で、発信者とオーナーを登録することもできる。
- 手順1で連携したアカウントが、オーナーが退会した発信者のものなら、その発信者を取り戻せる（4.6.1.2）。取り戻さずに新しく登録しようとすると、ほかの発信者で確認済みのアカウントとして断る。

> ##### 4.6.1.1 処理フロー
>
> 1. 2つの手順を、順不同で済ませる。
> 2. 利用規約・プライバシーポリシー・発信者向けの利用規約に、まとめて同意する。
> 3. 「発信者として登録する」を押す。
>
> <kbd>異常系</kbd>
>
> - 手順または同意が済んでいない　→　登録のボタンを押せない
> - ID が使われている・登録待ちの連携がほかの発信者で確認済みになった・受付を閉じている　→　それぞれの理由を知らせる
> - そのほかの失敗　→　失敗を知らせる

##### 4.6.1.2 発信者の取り戻し

- オーナーが退会した発信者（4.6.6.2）を、90日のうちに、新しいユーザーがオーナーとして引き継ぐ。発信者の ID・プロフィール・連携・予定・取得したデータは、そのまま。
- 本人の確かめには、SNS の連携を使う（退会で、ログイン方法のひも付けも消えるため）。手順1で確かめたアカウントが、取り戻せる発信者の確認済みのアカウントのどれか1つと同じなら、取り戻せる。
- はじめからオーナーがいない発信者（確認用の発信者など）は、取り戻せない（4.6.6.2）。
- 手順1で、取り戻せる発信者のアカウントを連携すると、断らずに登録待ちの連携に入れ、登録の画面に取り戻しの案内（発信者の名前と ID、取り戻せる期限）を出す。取り戻せる発信者が複数あれば、期限の遅い1人だけを出す。
- 取り戻しも、アカウント（ログイン方法）があるユーザーだけ。受付を閉じているときは、登録と同じく断る。
- 取り戻すのに、プランの加入は要らない。前のオーナーの X連携プランの加入は、新しいユーザーで「購入を復元」をすると引き継げる（4.6.6）。案内にも、そのことを出す。
- 取り戻すと、オーナーを新しいユーザーにし、ファンにまた見せる。登録待ちの連携は、発信者のアカウントに移す（前と違うアカウントなら、置き換える）。
- プロフィールの入力（手順2）と規約への同意は、求めない。登録のときに同意した発信者を、そのまま引き継ぐため。

> ###### 4.6.1.2.1 処理フロー
>
> 1. 発信者として登録の手順1で、SNS のアカウントを連携する。
> 2. 取り戻せる発信者のアカウントなら、登録の画面に戻り、取り戻しの案内を出す。
> 3. 「取り戻す」を押す。
> 4. オーナーにする。発信者メニューに入れる。
>
> <kbd>異常系</kbd>
>
> - 90日を過ぎた・その間にほかの人が取り戻した・連携したアカウントが合わない　→　もう取り戻せないことを知らせる
> - 登録待ちの連携がほかの発信者で確認済みになった・受付を閉じている　→　登録と同じく知らせる
> - そのほかの失敗　→　失敗を知らせる

#### 4.6.2 アカウント連携

| 項目 | 内容 |
| --- | --- |
| 機能概要 | SNS（YouTube・X・Instagram・ツイキャス・Twitch）ごとに、アカウントを連携し、本人のものであることを確かめる。連携は、いつでも解除できる |
| 事前条件 | 発信者として登録中、または登録の手順中 |
| 関連画面 | アカウント連携 |
| 入力項目・バリデーション | SNS（連携する・解除する） |

<kbd>補足・実装メモ</kbd>

- アカウントの状態は3つ。未連携（行がない）、未確認（運営が SQL で入れたが、確認が済んでいない）、確認済み。確認が済んでいないアカウントは、追星に表示しない。取得もしない。
- OAuth で連携し、確かめる。発信者が SNS にログインして許可すると、サーバーが本人のアカウントを引き、確認済みにする。前に入っていたアカウントと違えば、引いたアカウントに置き換える。
- 別のアカウントを選べるように、YouTube はアカウントを選ぶ画面を、Twitch と Instagram はログインの画面を、毎回出す。求める権限は、アカウントを引くのに要るものだけ（YouTube は `youtube.readonly`、Twitch はなし、X は `users.read`・`tweet.read`）。
- OAuth で受け取ったトークンは、アカウントを引いたらすぐ捨てる（取り消せる SNS は取り消す）。保存しない。取得は、アプリの権限で行う。
- 1つの SNS アカウントを確認済みにできるのは、1人の発信者だけ。ほかの発信者で確認済みのアカウントは、連携できない。
- 連携の解除は、確認済みのアカウントだけ。前に再認証する（4.1.4.1。ログイン方法がないときは求めない）。サーバーの関数（`unlink_creator_account`）で行う。確認のダイアログで、発信者として登録済みなら、90日残してから消すことと、連携し直すと元に戻ることを伝える。
- 解除すると、そのアカウントの内容（投稿・配信中の情報・取得した配信の予約・配信の実績）を、すぐにファンにもオーナーにも見せなくし、取得も止める。イベントの公演は、そのまま出す。取得した配信の予約と配信中の情報は、次の取得で消す（4.5.1・4.3.1）。
- 残りの内容（投稿・配信の実績）は90日持ち、過ぎたら、1日1回の定時実行（4.8.1）で、内容とアカウントの行を消す。90日のうちに同じアカウントを連携し直したら、元に戻す。違うアカウントを連携したら、持っていた内容をすぐに消す（内容は SNS ごとに持つので、新しいアカウントの内容と混ざるため）。
- 解除したアカウントは、確認済みでなくなる。ほかの発信者が、そのアカウントを連携できる（そのあとは、元の発信者では連携し直せない）。
- Instagram は、Instagram のログイン（Instagram API with Instagram Login、権限は `instagram_business_basic`）で確かめる。プロアカウント（ビジネス・クリエイター）だけがログインできる。トークンは取り消す口がないので、捨てるだけ（1時間で切れる）。取得は、Business Discovery で行う。
- Instagram は、アプリの役割（Instagram テスター）を持つアカウントだけが連携できる。役割のない発信者に開く手順は、今後の検討事項とする。
- **【仮】** Meta の審査が通るまでは、Instagram のログインの代わりに、DM で確かめる（4.6.2.1）。
- **v1.0.0 では、Instagram の連携を出さない**（決定事項 1。次の版で出す）。Instagram の行は、TikTok・ニコニコと同じ「準備中」にし、押しても連携や DM の手順に進まない。確認済みの Instagram があっても、連携の行には出さない。切り替えは、アプリのコードの1か所（`instagramOffered`）だけで、サーバーの設定（`instagram_dm_account`）では切り替えない。
- 発信者として登録の手順から開いたときは、確かめたアカウントを、登録待ちの連携に持つ（4.6.1）。運営が SQL で、発信者とアカウントを入れることもできる（`supabase/debug/creators.sql`）。
- 対応していないプラットフォーム（TikTok・ニコニコ。v1.0.0 は Instagram も）は、一覧に「準備中」として並べる。

> <kbd>異常系</kbd>
>
> - SNS の画面で、許可しなかった・閉じた　→　何もしない
> - ほかの発信者で確認済みのアカウント　→　ほかの発信者で連携されていることを知らせる
> - 時間切れ（10分）・通信の失敗・SNS の失敗・Instagram で役割のないアカウントや個人アカウント　→　失敗を知らせる
> - YouTube で、チャンネルのない Google アカウント　→　チャンネルが見つからないことを知らせる
> - 解除に失敗　→　失敗を知らせる

##### 4.6.2.1 【仮】Instagram の DM での確認

> **これは仮の仕組み。** Meta のアプリの審査とビジネス認証が通るまで、MVP を公開するための一時的な代わり（決定事項 5）。通ったら外す。本来の確かめ方は、4.6.2 の Instagram のログイン。

- 切り替え：運営が SQL で、`app_settings` の `instagram_dm_account` に、DM の受け先の Instagram のユーザー名を入れたときだけ、Instagram の「連携する」で DM の手順を出す。空か行がないときは、Instagram のログイン（4.6.2）に戻る。アプリを出し直さずに切り替えられる。
- v1.0.0 のアプリは、Instagram の連携を出さない（4.6.2）ので、受け先が入っていても、DM の手順を出さず、`instagram_dm_account` も読まない。次の版から使う。
- 発信者として登録の手順（4.6.1）からも、発信者メニューからも、同じ手順で確かめる。
- コードは、16進数の大文字8文字の使い捨て。期限は7日。1人のユーザーが持てるのは、発信者ごとに1つ（登録の手順からは1つ）。出し直すと、前のコードは使えなくなる。
- コードを出すときに、入れたアカウントの形と、ほかの発信者で確認済みでないかを確かめる。登録の手順から出すときは、取り戻せる発信者（4.6.1.2）のアカウントを断らない。
- 運営は、DM の送り主のユーザー名とコードを確かめ、関数 `approve_instagram_dm` を呼ぶ。送り主が、コードを出したときに入れたアカウントと同じときだけ、確認済みにする（結果は、データ設計書 3.3）。運営の手順は、`docs/dev/environment.md` 5.3。
- 確認済みにしたあとは、Instagram のログインで確かめたアカウントと同じに扱う（取得・表示・解除・90日の保持）。
- 確かめを待つあいだ、Instagram の行には「確認待ち」と出す。期限を過ぎたコードは、本人にも見せず（「確認待ち」にしない）、出し直せる。確認済みになったことは、通知しない。確認済みにできなかったときは、運営が DM で返事をする。
- 登録の手順から出したコードで、出した人がすでにオーナーなら、確認済みにせず `already_owner` で断る（4.6.2。登録待ちの連携は作らない）。

> ###### 4.6.2.1.1 処理フロー
>
> 1. Instagram の行の「連携する」を押す。DM の手順のシートを出す。
> 2. 自分の Instagram のユーザー名を入れ、「コードを出す」を押す。サーバー（関数 `request_instagram_dm`）が、コードを作る。
> 3. シートに、コード、受け先のアカウント、「Instagram で DM を送る」を出す。
> 4. 発信者が、入れたアカウントから、コードを DM で送る。
> 5. 運営が確かめて、確認済みにする。
> 6. 「確認待ち」の行を押すと、コードをもう一度見られる。「取り消す」で、コードを消す。
>
> <kbd>異常系</kbd>
>
> - ユーザー名の形が違う・ほかの発信者で確認済みのアカウント　→　それぞれの理由を知らせる
> - コードを出せない・取り消せない・ページを開けない　→　失敗を知らせる

#### 4.6.4 プロフィールの編集

| 項目 | 内容 |

| 機能概要 | 名前・アイコン・カバー・プロフィール文・タイプを編集する。連携済みの SNS から、名前・アイコン・プロフィール文を、下書きとして取り込める |

| 入力項目・バリデーション | 名前（必須、1〜100文字。見た目の1文字で数える。前後の空白は除く）、プロフィール文、アイコン、カバー、タイプ（任意、3つまで）、ID（登録のあとは変えられない。英小文字・数字・`_`・`-` の1〜40文字） |

<kbd>補足・実装メモ</kbd>

- タイプは、自分の発信の種類。おすすめ（4.2.2.2）で使う。表記がばらけないよう、決まった一覧（データ設計書 3.1.2）から、3つまで選ぶ。一覧の追加・名前の変更は、運営が SQL で行う（アプリを出し直さずに変えられる）。
- 名前は、入力欄と保存の確かめを、同じ数え方（見た目の1文字。絵文字も1文字）にする。データベースの上限は、余裕を持たせた最後の守りにする（データ設計書 3.1.1）。

<kbd>SNS からの取り込み</kbd>

- 取り込んだ項目は、保存するまで反映しない。「下書き」と、取り込み元を示す。
- 取り込み元に出すのは、確認済みの SNS だけ（発信者として登録の手順からは、登録待ちの連携）。
- X から取り込めるのは、X を取得する発信者（4.6.6）だけ。X の取り込みには、X の API の費用（1回約 1.6 円）がかかるため。
- 取り込みは、サーバー（Edge Function `fetch-profile`）が、アプリの権限で、公開のプロフィールを取る。本人のトークンは使わない（持っていない）。
- 取るのは、名前・プロフィール文・アイコン。カバーは取り込まない。取り込んだ名前は、100文字に収まるように切る。SNS で空の項目は、入っている内容を消さない。アイコンが取れなければ、名前とプロフィール文だけを入れる。
- 取り込みは、ユーザーと SNS ごとに、24時間で回数を区切る。X は5回まで（連打での課金を防ぐため）、ほかの SNS は20回まで（呼び出しの上限を、定時の取得と分け合うため）。失敗しても、1回と数える。

> ##### 4.6.4.1 処理フロー
>
> 1. 取り込み元の SNS を選ぶと、名前・アイコン・プロフィール文が、下書きとして入る。
> 2. 編集して、「保存」を押す。
> 3. 内容を保存して、前の画面に戻る。
>
> <kbd>異常系</kbd>
>
> - 名前・ID の形が違う　→　保存せず、どこが違うかを出す
> - 取り込めない・取り込める項目がない・回数の上限を超えた　→　それぞれの理由を知らせる
> - タイプの一覧を読み込めない・保存に失敗　→　失敗を知らせる

#### 4.6.5 予定のデフォルトの長さ

- 廃止した（2026-11-19 本人「『予定のデフォルトの長さ』ちょっとこれよくないわ」）。発信者が長さを決める設定と、その画面を無くした。番号は、ほかの文書とコードから指しているので残す。
- 代わりに、終了時刻のない予定は、イベント（プラットフォームのない予定。公演）はその日の終わり（24:00）まで、配信などは1時間で描く（4.5.3）。終了時刻のない公演は、その日の終わりまで、終端をフェードさせて描く。
- イベントの管理で過去に分けるのも、終了時刻のない公演は、その日が終わってから。
- サーバーの `creators.default_event_minutes` と `creator_event_lengths`（データ設計書 3.1.1・3.1.10）は、公開中の v1.0.0 のアプリが読み書きするので、今は残す。この版から、アプリは読まない・書かない。消すのは、v1.0.0 の利用者がいなくなってから（開発環境 11.6 の2段の2段目。Issue に残した）。

#### 4.6.6 プラン

| 項目 | 内容 |
| --- | --- |
| 機能概要 | 発信者のプランを確かめ、X連携プランに加入・解約する |
| 事前条件 | 発信者として登録中 |
| 関連画面 | プラン |
| 入力項目・バリデーション | 「X連携プランに加入する」ボタン |

<kbd>補足・実装メモ</kbd>

- 基本プランは、料金がかからない。登録すれば、YouTube・Instagram・ツイキャス・Twitch の取得と表示（v1.0.0 は Instagram を除く。4.6.2）、配信の予約の取得、イベントの登録を使える（decisions.md）。
- X の連携は、有料のプラン（X連携プラン。月290円）。X の API に費用がかかるため。お試し期間は設けない（基本プランを無料で試せるため）。
- プランの種類は4つ（2.1）。永年無料・運営・確認用は、運営が SQL で入れ（`creators.plan`）、X連携プランに加入しなくても、X の連携を使える。画面には、料金がかからないことを出し、加入と解約は出さない。
- 基本プランの発信者には、X連携プランの加入の状態（加入中なら次の更新日、解約したなら終わる日）を出し、加入と解約もここから行う。
- X を取るのは、X連携プランの期限がいまより後か、永年無料・運営・確認用のとき。支払いの猶予期間のあいだも、加入中として扱う。切れたら、X だけを止める（4.6.3）。

<kbd>課金</kbd>

- App Store・Google Play のアプリ内課金（自動更新のサブスク）で行う。購入の検証と、更新・解約・返金の受け取りは、RevenueCat に任せる（decisions.md）。商品は「X連携プラン」の1つ。RevenueCat の Offering は `default`（なければ、現在の Offering）、パッケージは `$rc_monthly`（`creator_x_monthly`）、Entitlement は `x_option`。
- RevenueCat のユーザー ID は、Supabase のユーザー ID（匿名を含む）にそろえる。ユーザーが変わったら、RevenueCat のユーザーも切り替える。
- アプリは加入の状態を書かない。サーバーが、RevenueCat の Webhook を受けたときと、アプリが購入・購入の復元をしたあと（Edge Function `sync-subscription`）に、RevenueCat の API に加入の状態を問い合わせて、ユーザーの加入を書く（データ設計書 3.1.11）。Webhook の中身は信じない。発信者の加入は、オーナーからたどる。
- プランの画面の表示は、ストアの購入から決める（サーバーの加入の状態は、Webhook の分だけ遅れるため）。
- 購入の復元で、購入がほかのユーザーから移ったとき（TRANSFER）は、移した元と先の両方の加入を書き直す。移した元が退会したユーザーなら、書かない（4.6.1.2）。
- 解約は、ストアのサブスクの管理の画面で行う（アプリからは、その画面を開く。再認証の対象にしない。4.1.4.1）。解約しても、次の更新日までは加入中のまま。
- 機種変更や入れ直しのために、購入の復元を置く（App Store の審査で必須）。
- 価格は、ストアの値（その国の通貨）を出す。読めないときだけ、アプリに持つ月額（290円）を円で出す。
- その端末の RevenueCat のキーがなければ、課金を使えない。Android のキーは空なので、Android では課金を使えない。

> <kbd>異常系</kbd>
>
> - 支払いの承認を待っている・復元できる購入がない　→　そのことを知らせる
> - 購入・復元に失敗　→　失敗を知らせる
> - ストアの商品がそろわない　→　「読み込めない」の状態を出す

##### 4.6.6.1 （欠番）

- 基本プランが無料なので、加入が切れて取得と表示を止める状態はない。X連携プランが切れたときは、X だけを止める（4.6.3）。番号は、ほかの文書とコードから指しているので残す。

##### 4.6.6.2 オーナーが退会した発信者

- オーナーが退会して、オーナーがいなくなった発信者。オーナーがいなくなった時刻（`creators.owner_left_at`）を持つことで、はじめからオーナーがいない発信者（確認用の発信者など）と区別する。時刻は、オーナーの行が消えたときにサーバーが入れ、オーナーの行を入れたとき（取り戻し、運営の SQL）に消す。
- プランにかかわらず、取得をすべて止め、ファンには発信者ごと見せない（発信者ページ・検索・おすすめ・推しリスト。投稿・配信・予定・実績も、ホーム・スケジュール・月のカレンダーに出さない）。ファンのフォローは消さない。
- 90日を過ぎたら、1日1回の定時実行（4.8.1）で、発信者ごと消す（登録の情報・連携・予定・取得したデータ・実績・フォロー・画像）。
- 90日のうちなら、取り戻せる（4.6.1.2）。取り戻すと、表示と取得を戻す。
- 発信者の SNS のアカウントは、90日のあいだ、確認済みのまま残す。ほかの発信者は連携できない（取り戻しにだけ使える）。

### 4.8 サーバー

#### 4.8.1 定時実行

| 項目 | 内容 |
| --- | --- |
| 機能概要 | pg_cron が、Edge Functions と SQL の関数を一定の間隔で呼び、配信の確認・投稿・予約・フォロワー数・実績の取得と、期限を過ぎたデータの削除を動かす |
| 事前条件 | 本番の Supabase の設定済み（接続先と合言葉は、Vault に置く） |
| 関連画面 | なし |
| 入力項目・バリデーション | なし |

<kbd>補足・実装メモ</kbd>

| 処理 | 間隔 | 内容 |
| --- | --- | --- |
| 配信の確認 | SNS ごとに設定（既定は1分ごと。4.8.1.2） | 4.3.1 |
| 投稿の取得（YouTube・X） | 1分ごと | 4.4.1 |
| 投稿の取得（Instagram） | 設定（既定は15分ごと。4.8.1.2） | 4.4.1 |
| 配信の予約の取得 | SNS ごとに設定（既定は30分ごと、毎時7分・37分。4.8.1.2） | 4.5.1 |
| フォロワー数の取得 | 1時間ごと（毎時23分） | 4.2.5 |
| 終わった配信の取得（ツイキャス・Twitch） | 1時間ごと（毎時53分） | 4.5.4 |
| 解除して90日を過ぎたアカウントの、内容の削除 | 1日1回（日本時間の4時27分） | 4.6.2 |
| オーナーが退会して90日を過ぎた発信者の削除 | 1日1回（日本時間の4時37分） | 4.6.6.2 |
| YouTube で消えた動画の削除と、配信の実績の取り直し | 1日1回（日本時間の4時47分） | 4.4.2・4.5.4 |
| 予定の事前通知 | 1分ごと | [届ける・広める](functional-spec-reach.md) 4.1.1 |
| 追いたいの人の登録の、自動のフォローと通知 | 5分ごと（一致があるときだけ Edge Function を呼ぶ） | [届ける・広める](functional-spec-reach.md) 4.5.2 |
| 発信者に見せる数の集計と、ユーザーを含む記録の削除 | 1日1回（日本時間の0時5分） | [届ける・広める](functional-spec-reach.md) 4.2.1 |

- アプリは、SNS を直接呼ばず、データベースだけを読む。SNS のキー・トークンは、サーバー（Supabase のシークレット）だけに置く。
- アプリは、表示中の一覧を1分ごとに読み直す。リアルタイムの購読は使わない。
- 呼び出しには、合言葉（`x-cron-secret`）が合うときだけ応じる。外から直接呼ばれないようにするため。
- 解除したアカウントの内容の削除は、SNS を呼ばないので、pg_cron が SQL の関数（`purge_unlinked_accounts`）を直接呼ぶ。発信者に見せる数の集計も同じく、SQL の関数（`aggregate_reach`）を直接呼ぶ。
- オーナーが退会した発信者の削除は、画像（Storage）を SQL から消せないので、Edge Function（`purge-left-creators`）を通す。画像を消してから、発信者を消す。画像を消せなかった発信者は、次の日にやり直す。
- YouTube で消えた動画の削除は、保存している YouTube の投稿の全部を対象にする（日付で区切らない。表示するコンテンツに関わらない。YouTube API の規約の保管の期限に合わせるため）。

> ##### 4.8.1.1 処理フロー
>
> 1. 定時の時刻になると、pg_cron が、Edge Function を呼ぶ。
> 2. 合言葉が合わなければ、実行せずに断る。
> 3. 同じ処理の鍵を取る。取れなければ、その回は飛ばす（取り込みが二重に走らないようにするため。オーナーが退会した発信者の削除は、鍵を取らない）。
> 4. 処理を実行し、終わったら鍵を返す。鍵には期限があり、期限を過ぎても前の実行が続いていれば、次の回は並べて実行する。

##### 4.8.1.2 取得の間隔の設定

SNS の呼び出しの上限に合わせて、取得の間隔を、運営が SQL で変えられるようにする（`app_settings`、データ設計書 3.1.24）。デプロイは要らない。発信者ごとには変えない（全員が同じ間隔）。

| キー | 対象 | 既定 | ずらし |
| --- | --- | --- | --- |
| `fetch_interval_lives_twitcasting` | 配信の確認（ツイキャス） | 1 | 0 |
| `fetch_interval_lives_twitch` | 配信の確認（Twitch） | 1 | 0 |
| `fetch_interval_lives_youtube` | 配信の確認（YouTube） | 1 | 0 |
| `fetch_interval_posts_instagram` | 投稿の取得（Instagram） | 15 | 0 |
| `fetch_interval_schedules_twitcasting` | 配信の予約の取得（ツイキャス） | 30 | 7 |
| `fetch_interval_schedules_twitch` | 配信の予約の取得（Twitch） | 30 | 7 |
| `fetch_interval_schedules_youtube` | 配信の予約の取得（YouTube） | 30 | 7 |

- 値は、分の整数（1〜1440）。行がない、または値が正しくないときは、既定を使う。
- 取る回は、UTC の 1970-01-01 0時0分からの分数を、間隔で割った余りが、ずらしと同じ回。間隔が60の約数なら、毎時同じ分に取る。
- pg_cron は、配信の確認・投稿の取得（Instagram）・配信の予約の取得を、1分ごとに呼ぶ。関数は、設定を読んで、その回に取る SNS を決める。
- Edge Functions の呼び出しは、定時実行で月 約221,000回（予定の事前通知の1分ごと、月 約43,200回を含む）。Free の50万回に収まる。
- 投稿の取得（YouTube・X）は、1分ごとのまま（YouTube は RSS で上限がなく、X は呼び出しではなく取れた件数で課金されるため）。
- 配信の確認で、その回に確かめない SNS は、次のように扱う（4.3.1）。
  - 配信中の行がその SNS のものなら、配信中のまま残し、確認した時刻だけ新しくする（アプリの「3分を超えたら配信中とみなさない」を変えないため）。通知と、配信の実績の記録はしない。
  - 配信中の行がない、またはほかの SNS のものなら、その SNS では配信していないとみなす。
  - そのうえで、ツイキャス → Twitch → YouTube の順で、1つだけ出す。
- 間隔を延ばすと、配信が終わったあとも、次の確認まで配信中のまま出る。
- 配信の予約の取得で、対象から外れたアカウントの予約を消すのは、どれかの SNS を取る回だけ。
